# 引导式变更演练与生产 SOP

平台对「首次部署」与「投产后变更」严格分层：
- **首次部署**：机器干净、拓扑与版本受控，由平台确定性生成离线包、Ansible 剧本与验收测试。
- **投产后变更**：生产环境往往已发生过主从切换、参数微调、补丁安装或架构漂移，不能在缺少现场真实状态的情况下盲套静态自动化剧本，必须通过集群「变更演练」分四步完成。

## 第一步：诉求与边界对齐（scoping）
- 读取集群首次交付的基线拓扑、软件包锁定版本、参数与对外入口（VIP/负载均衡）。
- 明确询问 2～4 个影响实施路径的核心边界：可接受的维护窗口与闪断时长、离线目标包或新增节点是否就位、客户端重连机制、测试演练环境规模。

## 第二步：纯只读现场采集与漂移诊断（probing）
- 生成在生产节点执行的 **100% 纯只读** Bash 采集脚本：只允许状态查看、角色与复制延迟查询、非敏感配置读取、端口与磁盘内存检查。
- 严禁包含任何写入、删除、重启、切主、装包、改配置或重定向写文件指令（仅允许重定向到 `/dev/null`）；严禁输出密码、密钥或 Token 明文。
- 将现场回显与首次交付基线逐项比对，重点识别：当前真实主从角色是否已漂移、当前实际运行版本、被手工修改过的关键参数以及潜在冲突风险。

## 第三步：测试环境分步演练与排障打磨（rehearsing）
- 生成涵盖 `precheck`（变更前预检）、`execute`（严格遵循先备后主与平滑切换顺序）、`verify`（变更后验收）和 `rollback`（应急回退）的分步清单。
- 每一步必须写明执行对象、完整命令、明确的成功判据与本步即时回退方式。
- 演练过程中若某步报错，先根据实际报错输出定位根因，再通过 `replace`（原地修正命令）或 `insert_before`（补充前置准备步骤）更新演练清单，直至所有必测步骤在测试环境实测通过并记录真实耗时与注意事项。

## 第四步：定稿《生产变更实施方案》（finalized）
- 仅当测试环境必测步骤全部验证通过后，才允许定稿生产 SOP。
- 定稿文档必须把测试环境打磨通过的最终命令、实测耗时、注意事项与回退红线映射到第二步核实的生产真实节点与当前主从角色上，支持在集群「文档」页复核签字并导出标准 Word（`.docx`）。
