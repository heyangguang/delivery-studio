# 组件编写规范

## 平台离线命令入口（必须遵守）
- 本平台交付只提供 bin/ansible-playbook 和 bin/ansible-inventory，没有 bin/ansible；也不能假设系统 PATH 中有 ansible。
- 先读取当前交付手册或 controllerFacts，确认项目目录、控制节点、inventory 和实际 playbook 路径。执行时使用 cd 到项目目录后的 ../../bin/ansible-playbook 或已核实的绝对路径；查看清单用 ../../bin/ansible-inventory -i inventory/hosts.yml --graph。
- 不得生成裸 ansible 或 /root/middleware-automation/bin/ansible 命令。ansible-playbook 不能接收 ad-hoc 的 -m/-a 参数，不能机械替换命令名。
- 单机排查：明确告诉用户在哪台目标机器上执行，并提供该机直接执行的只读 shell 命令。需要跨机器检查时优先使用已存在且已核实的 playbook；确需临时 playbook 则必须给出完整 YAML、保存位置和调用命令，不要虚构已存在的文件。
- 旧对话、知识库或用户截图中出现 bin/ansible 不代表该入口存在；应纠正旧命令，不要沿用。

开始前用 component_guide 读相关章节（4.1 清单结构、4.2 参数、4.4 生命周期、4.5 测试、16.11 变更步骤、17 步骤独立性、17.1 输入与结果契约、18 系列契约、19 多文件清单与方案表单），并参考一个结构相近的现有组件。

## 步骤隔离（所有组件统一遵守）
- 部署、测试、清理、变更动作都使用稳定步骤 ID；调整顺序不能改变步骤身份。
- 每个业务动作有独立任务、脚本入口和模板。修改 A 的私有实现只能影响 A，不能顺手改 B/C，也不能用一个大脚本按动作分支承载所有步骤。
- 真正共用的文件必须在组件顶层 shared_files 用精确路径声明。修改公共文件会影响全部使用者，提案必须说明这个范围；禁止把所有文件标共享来绕过归属检查。
- 步骤输入使用 inputs 的 {type, value} 契约，类型为 string/int/bool/list/map，通过 mw_step_inputs 读取。只引用本步骤需要的配置，避免无关参数进入脚本或模板。
- 用 preconditions / postconditions 声明执行前后检查（不带模板分隔符的 Ansible 表达式）。失败不得报告成功；结果遵循平台 STEP_RESULT 的 mwstep-result/v1 契约，不伪造其他步骤的结果。
- 提交前运行 run_check，修复归属、引用、类型等平台错误。不能通过忽略错误或扩大共享范围来规避约束。
- 修改后验证同步影响范围：私有文件或独立输入仅命中该步骤；共享文件命中实际使用者。没有验证就明确说明，不能声称已经隔离。

## 清单
- 只用指南里定义的字段；参数要有类型、默认值、范围和中文说明。
- 角色写清最少数量、是否需要奇数、是否互斥；硬性上限只用于真实约束。
- 依赖用 `requires` 声明能力，不要直接写死另一个组件。

## 任务
- 幂等：重复执行不产生变化；用模块而不是 `shell`，必须用 `shell` 时加 `creates`/`changed_when`。
- 先检查再改：安装前确认版本、配置前备份、启动后等待健康。
- 会中断服务的步骤单独成阶段，并在手册里标明。
- 密码和密钥由平台的 secrets 机制生成和分发，任务里引用变量，不写明文。

## 测试与验证
- 功能测试要能区分成功与失败（明确的通过标准）。
- 清理步骤只清理测试资源。

## 变更步骤（升级、扩容、缩容）
- 用 `added:`、`existing:`、`removed:` 选择主机；逐台滚动，每台后验证。

## 提交
- 用 propose_files 一次给出能通过检查的完整改动；平台检查报错时按提示修正。

## 改已有组件（尤其是长的 component.yaml）
- 先用 draft_search 定位并读取相关片段及依赖；draft_read 截断时用 from_line 补齐必要上下文，不为小改动通读所有文件。
- 局部修改：propose_files 的每个文件用 edits（原文 → 新内容，原文必须在文件里恰好出现一次），不要整文件重写，避免覆盖掉没读到的部分。
- 加扩展、参数、检查这类小改动，先找到同类的已有写法，照它的格式追加。

## 部署方案与管理组件
- 常见架构由组件 presets 声明；例如 PG 的 single、replication、patroni 三种方案。不能用“有从库”推断用户需要自动高可用。
- 数据库和管理器是独立组件。父组件用 companions 声明启用条件、组件名、管理能力；管理器用 context 指向已声明的 requires 能力。平台自动展开并校验节点、管理对象与唯一管理权，不允许两个管理器接管一个数据库。
- 管理步骤中 mw 是被管理数据库，mw_manager 才是管理组件自身。数据库身份、密码、证书、业务入口沿用 mw；管理器的软件包和协调存储依赖读取 mw_manager。不要混合整个对象，否则无法准确识别步骤变更范围。
- etcd 依赖属于 Patroni；普通 PG 主从不引入 etcd。etcd 统一由平台部署和管理，不再提供 external-etcd 外部连接组件或复用已有 etcd 的参数。
- 每种方案必须覆盖条件校验、生成、语法、同步影响测试。旧交付没有方案字段时保留原有行为，不自动迁移。


### 面向用户的方案名称
使用能力名称而非技术组件名作为方案标题：基础系列（单节点）、主从系列（原生复制、人工切换）、高可用系列（自动故障切换）；真正提供数据分片时才使用“分片集群系列”。PostgreSQL 例外：标题统一使用「单机方案」「原生主从方案」「Patroni 主从方案」，对应 single / replication / patroni，保持内部 ID 和 basic/replication/ha 能力契约稳定；禁止以“高可用系列”代替 Patroni 方案名称。Redis 等其他组件遵循同一命名原则，但只展示实际实现并验证的方案，不能因为多节点就承诺分片或自动切换。卡片说明必须写明节点结构、切换方式和适用限制；不要照搬云产品的存储分离、备节点不可访问等未实现能力。

## 系列契约与发布门禁（必须遵守）
- 每个 detail.presets[] 必须填写 contract，新组件模板里的缺失契约是待完成项，不能只改软件版本就发布。
- series 使用 basic / replication / ha / sharded，显示名分别为基础系列 / 主从系列 / 高可用系列 / 分片集群系列，可用“ · 规格”区分同系列规格。
- when 是识别该架构的表达式；不要把内存大小、TLS 等可调参数当作架构标识。预设自己的角色和参数必须满足它，同一配置不得同时匹配多个系列。
- failover 明确 none / manual / automatic；mechanism 描述真实机制；read_access 说明主从读写能力；sharding 只有实际提供数据分片才为 true；limitations 不能缺省。
- acceptance 引用“组件名/测试ID”，测试必须存在、含 expect，并在该方案启用；跨组件验收只能引用参与本方案的组件。声明验收不等于已经执行通过，不得把待验证版本改为已验证。
- operations 明确声明组件支持的首次部署操作 `[deploy]`。平台组件清单专注确定性的首次部署、高可用验收测试与现场清理，不在组件清单中预制投产后的派生变更剧本。
- 旧清单缺少契约可以继续读取，但编辑发布会被阻止；禁止删除 presets、改名或扩大能力声明来绕过门禁。修复真实能力与测试，不修改标准迁就组件。

## 19 多文件清单与方案表单

component.yaml 是组件唯一入口，使用 {$file: manifest/...yaml} 引用独立 YAML 文件。引用映射只能含 $file；路径相对组件根目录，只允许 manifest/ 下 .yaml 文件，不允许路径回退、循环引用、重复归属和 YAML 别名。每个文件一个 YAML 文档。

- 公共参数、角色、版本等写入 manifest/common/；每个部署方案写入 manifest/schemes/<稳定ID>.yaml；首次部署生命周期阶段写入 manifest/actions/，测试和清理各步骤独立成文件。
- 一个中间件仍是一个组件，方案共享公共定义，不复制成三个组件。界面部署方案标签每次仅编辑一个方案；切换方案同步节点、角色、参数和条件依赖。基础系列只保留其需要的节点；其他组件实际占用的节点不能误删，已填写地址的移除须确认。
- 修改前读取入口并沿 $file 找到实际所属文件，只修改所属片段。不要把分片重新内联到 component.yaml，不要为小改动重写全部清单。新增方案同时提交片段和入口引用；引用文件与入口必须一起通过 run_check。
- 文件拆分只改变存储组织，不代表步骤实现独立。仍须遵守第17章私有实现、精确共享依赖和输入契约，验证修改A不影响B/C。
- 旧单文件清单仍可读取；禁止覆盖已有草稿或自动改变历史交付。迁移必须验证展开后语义一致、各方案预览和同步影响范围。

## 交互与历史架构说明
- 新建集群默认进入AI填写界面，允许随时切换手工表单，切换不清空配置。仅切换页面、模式或载入默认预设，不视为用户填写，不创建空草稿。
- 表单复用公共字段组件；标签、控件、帮助文字保持固定顺序，开关左对齐，恢复默认值紧邻对应字段，不单独拼接尺寸或将长说明挤到开关同一行。
- 历史交付缺少方案快照时，展示保存的实际角色和节点；识别具体架构必须提供当时交付的证据。Patroni架构需明确的Patroni端口及关联协调存储，不能只凭三台机器推断高可用。识别结果是只读说明，不补写历史、不授予变更操作，也不表示现场重新验收。

## 平台公共流程
- 遇到 mw_preflight、mw_data_disk、mw_offline_repo、mw_packages 或 mw_secrets，使用 platform_files 读取公共代码、files/platform-contract.md 和 generated/inventory/group_vars/all.yml。不能因为当前在 Redis/PG 工作台就声称看不到公共角色。
- 公共角色修改使用 propose_platform_files，返回的工作台链接必须告诉用户；用户在那里审核、采纳并发布。当前组件的私有代码继续使用 propose_files，两份提案要说明兼容关系与发布顺序。
- 公共机器参数在 manifest/host-parameters.yaml 定义：支持string/int/bool/enum、默认值及条件规则。通过 propose_platform_files 同时修改参数定义与使用参数的公共任务，创建表单、后端校验、hosts[].params传参自动接入；无需改平台源码。先读 files/platform-contract.md，不要虚构Host顶层字段。
- 公共修改应只影响使用它的步骤；试生成 Redis、PostgreSQL、etcd，检查影响范围。发布不等于执行，不能自动对运行集群执行变更。

## 生效边界
采纳只改草稿，发布需通过校验并由用户确认；发布用于新生成和同步，不代表现有集群已执行。公共参数放 hosts[].params，组件参数放 instances[].params。修改共享文件影响实际使用者，不能承诺只影响一个步骤。

## 跨公共流程和组件的修改（必须遵守）
- 当前工作台不是修改范围的限制。用 workspace_search 在 live 和 draft 两个视图分别搜索路径、参数和公共角色引用；结果按 offset 分页，不能把第一页当成全部。draft 只查已存在草稿，不混用已发布版本。
- 用 component_files 指定 name、view、path 读取关联组件，公共流程 name 为 platform-shared。修改前必须读取目标草稿；没有草稿时先读 live，提案工具会以已发布版本准备草稿，不覆盖他人的现有草稿。
- propose_component_files 可向任意已发布组件（含公共流程）提交 summary/files 提案，无需用户切换聊天。每份提案仍走静态检查、试生成和可用的语法检查，采纳后才写草稿。必须把每个目标的审核链接交给用户，在新标签页打开。
- 采纳相关提案后调用 check_workspace，names 明确列出这次修改的草稿。也可让用户点击工作台顶部“联合检查”，选择相同草稿。其他组件使用已发布版本；尚未采纳的提案不会参加检查。
- 联合检查包含静态校验及各部署方案默认版本的生成，不等于所有软件版本、操作系统或现场执行验收。说明未验证范围，不得声称已部署。
- 跨组件修改要设计兼容发布顺序：消费新增公共参数时先使用兼容默认值，公共参数先发布、消费者再发布；不能要求几个独立发布动作原子生效。存在不兼容窗口时明确阻止直接发布，不能只凭联合检查通过就称可上线。
- 以自定义挂载点为例：搜索 /data、数据目录参数、挂载检查、备份及恢复路径；修改参数定义并不自动重写这些引用。检查公共预检、磁盘准备和所有实际使用者是否读取新值，保留旧交付路径。不做无差别文本替换，不把已有数据目录变更当成普通配置更新。
- 平台Go/TypeScript核心代码不属于工作台可编辑文件；若需求超出现有声明式参数/规则和任务文件能力，指出准确的字段或接口限制。不得伪造已实现能力，也不能笼统声称“只能修改当前组件”。

## 可配置挂载点与动态表单
- 公共参数 manifest/host-parameters.yaml 中的 data_root 是机器挂载点/数据根目录，默认 /data，类型 path。用户要求 /middleware 等目录时填写 hosts[].params.data_root，不修改磁盘设备字段来代替挂载点；独立盘与系统盘目录都支持。
- 在平台公共流程“参数与规则”新增 string/path/int/bool/enum 参数并发布，创建交付页面自动出现相应控件，校验及传参自动读取定义；组件私有参数由组件“参数”页定义。新增字段还必须让相关任务消费，不能仅凭出现输入框就声称业务实现。
- 读取当前公共参数契约；用平台公共流程和关联组件提案实现，联合检查。data_root 的变更不自动迁移已有数据；不通过普通改配置偷偷移动已运行集群目录。

## 交付能力与自动执行（1.0.242）
- 顶层 delivery_modes 可组合声明 offline（离线包）、automatic（执行节点自动执行）、configuration（仅配置）。未声明的旧软件组件维持离线模式；不能声称已有交付自动获得新能力。
- automatic 必须为每个生命周期、测试和清理步骤填写 timeout（1–86400 秒）、非空 postconditions 和 expect。完成条件验证真实结果，不可填 true 敷衍；任务本身也要保留输入/前置条件与 no_log。没有合格条件就保留离线能力，平台发布门禁不会通过。
- 自动执行使用同一份独立步骤与文件，不复制另一套自动化流程。运行时按固定交付快照执行，失败不自动重试，文本 rollback 不是自动回滚命令。
- configuration 对软件组件需要顶层 configuration: [{path: redis.conf, content: "…"}]，在概览的「配置文件」表单可编辑。只进行字面占位替换，支持 ${cluster}、${instance}、${params.<key>}、${host.name}、${host.ip}、${host.data_root}；不支持 Jinja、lookup、脚本或密钥读取。输出按实例/机器分目录，路径必须相对、不重复。复杂配置仍应走已有 Ansible 模板交付，不能假装已渲染。
- 发布窗口会再次让用户选择交付方式，并校验所选能力。仅出配置不执行安装，生成配置也不等于现场已应用。

## 执行位置与接入契约
组件步骤的 hosts 必须指实际业务角色：数据库本机验收应使用 first:primary 等角色；controller 只用于编排机上的工作，不能假设它装有 psql 或 redis-cli。需要节点间 SSH 的测试先做只读权限检查，禁止自动建立全互信。连接与 Agent 授权由平台管理，组件不得读取或分发执行器令牌/私钥。

## 工作台沙箱静态校验（可用时）
在组件工作台审阅或改写模板与脚本时，若可用 `run_shell` / `run_python` 且工具支持 `workspace` 参数，可设 `workspace=true` 将当前组件工程脱敏只读挂载到 `/workspace`（`$MW_WORKSPACE`），运行脚本 `bash -n` 语法校验、YAML/变量引用一致性检查或离线测试。`/workspace` 始终只读，实际改动仍必须通过 `propose_files` / `propose_platform_files` 提案交由用户确认并发布，不得尝试读取已被平台过滤的凭据或把沙箱环境当作客户目标系统。
