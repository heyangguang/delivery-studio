# 引导式变更演练与生产 SOP

平台对投产后的运维操作实行**「零未留痕变更」分级治理**，既避免流程臃肿，又保证每一次改动都有《变更报告》可查：
- **首次部署**：机器干净、拓扑与版本受控，由平台确定性生成离线包、Ansible 剧本与验收测试。
- **纯只读查询（零修改，不进演练）**：仅查状态、看日志、查主从/连接/复制延迟或核对现状，不改动任何配置或文件，直接在对话给 1～3 条只读命令即可。
- **极速变更（`mode="quick"`，2 步直达）**：只要涉及配置/参数/规则修改，哪怕非常轻量（如在线 `reload` 调整 `log_filename` / `log_rotation_size`、补单条明确规则）且现状已在对话或截图中明确、无需重启和切主，也**必须**发起 `mode="quick"` 进入演练工作台——直接跳过边界问答和只读探针，生成 2～3 步极简执行清单，跑完一键归档《变更报告》。
- **简单推演（`mode="light"`，3 步流程）**：要改配置/补规则/动态调参且无需重启切主，但现场状态拿不准需要先跑一屏只读探针核实，跳过边界问答直接走「只读探针 → 快速执行 → 归档《变更报告》」；若属组件模板遗漏，同时输出「组件改进建议」卡片。
- **全量推演（`mode="full"`，4 步完整流程）**：涉及滚动重启服务、主备切换、版本/CVE 补丁升级、扩缩容、备份/WAL 架构改造、TLS 证书轮换等高风险变更，走「边界对齐 → 只读探针 → 完整测试演练 → 定稿生产变更 SOP」。

## 第一步：诉求核对与边界对齐（scoping）
- 读取集群首次交付的基线拓扑、软件包锁定版本、参数与对外入口（VIP/负载均衡）。
- **诉求完整度前置门禁**：若用户描述简略模糊（如「看这个截图有点问题」「帮我看下报错」「改下配置」）或主要依赖截图反推意图、尚未明确具体变更目标与处理方式，**严禁跳过确认直出探针或步骤**，必须先停在「诉求核对与边界对齐」（`intent_unclear=true`），把识别到的现象与拟处理方向清晰写入 `scope_summary`，并把第 1 题用于核对与补全真实诉求，同时允许用户随时点击「修正诉求」改写并重新研判。
- **按变更复杂度克制提问**：轻量变更只问 1～2 个真正影响执行的点（严禁硬凑停机窗口、离线包或备份恢复等无关问题）；中高风险变更再询问 2～4 个核心边界（维护窗口与闪断口径、离线包/节点就绪度、应用重连、测试环境条件）。

## 第二步：纯只读现场采集与漂移诊断（probing）
- **基础身份头必采 + 变更项极简聚焦（一屏可读、严禁发散）**：
  - **1～2 行基础身份头（必采，对齐下游漂移表 5 列）**：无论是否涉及升级，脚本开头都必须用 1～2 行输出节点名（`hostname -s`）、本机 IP、**主组件及关键伴随组件实测版本号**（如 `SHOW server_version` + `patroni --version`、`redis-server -v`、`nginx -v`、`etcd --version`）以及当前真实主从/集群健康状态，避免下游漂移表出现「待采集」；
  - 其余部分只采与本次变更直接相关的 2～5 个核心参数/目录权限/目标目录磁盘余量，终端总输出控制在约 **15～35 行以内**，确保堡垒机或 VDI 环境下工程师靠 **1 张截图**即可完整回传。
  - 脚本保持简短直接（3～5 个检查块、总行数尽量不超过 45 行），不要写大段辅助函数或无关系统全量巡检；
  - 严禁 `cat` 整份配置文件，严禁无过滤打印长列表（如全量 `pg_hba.conf`、全量 `dpkg`/`rpm`、全量 `ss`/`ps`/`sysctl`、大段 `journalctl`、整机几十个挂载点的 `df -h`——只查 `df -h <目标路径>`）；
  - SQL/CLI 查询应精准取字段（如 `psql -Atc` 仅查目标参数）。
- **严格纯只读与脱敏**：生成 100% 纯只读 Bash 采集脚本（带 `BASH_VERSION` 自保护防 `sh` 误跑失败），严禁包含任何写入、删除、重启、切主、装包、改配置或重定向写文件指令（仅允许重定向到 `/dev/null`）；严禁输出密码、密钥或 Token 明文。
- **规避 ELB / 四层负载均衡同机回环（Hairpinning）**：后端数据/中间件节点本机执行探针时，**不要**在只读采集脚本里直连指向自身的云 ELB / SLB / LVS VIP（主库本机直连指向自身的四层 VIP 容易触发回环超时误判）；节点本机只查本地监听与 `127.0.0.1`/本机 IP。验证 ELB/VIP 写入入口时，优先使用集群外客户端/跳板机；**若现场没有独立跳板机，可在非当前主库的从库节点测试**（连向不同机器上的主库，通常不会触发同机回环；若仍受云 ELB 策略限制超时，该步可设为可选跳过，以本机健康接口与业务端验证为准）；只要从非主库连 VIP **实际连通并返回了基线中目标主库的 IP 且可写**，即为有效通过证据，严禁教条拒收。
- **采集有效性门禁与漂移比对**：若现场回显/截图显示脚本报错中断或未拿到核心状态，必须先阻断并给出修复重跑命令，绝不编造全是「未知」的漂移表；确认拿到有效现场状态后，再与首次交付基线比对角色漂移、版本、人工改参与风险。

## 第三步：分步演练与排障打磨（rehearsing）
- 生成涵盖 `precheck`（变更前预检）、`execute`（严格遵循先备后主与平滑切换顺序）、`verify`（变更后验收）和 `rollback`（应急回退）的精简可执行清单：简单推演控制在 **3～4 步**，常规全量推演控制在 **5～8 步**，单步命令尽量 **1～6 行**，不堆砌冗长巡检或几十行脚本框架。
- **变更临时状态复位与现场收尾铁律（做了什么临时变动，就必须原样弄回来！）**：
  - 凡是变更/演练过程中为了配合操作、降低风险或做验收而临时引入的任何状态改动，**都必须在正向流程的收尾/验收阶段安排显式的「复位/恢复/清理」步骤**（除非用户在诉求或边界对齐里明确要求保留新状态），绝不能改完不管，也绝不能只塞在应急回退（`rollback`）里！
  - 生成步骤前必须逐项核对以下 **6 类常见临时变动**，命中哪项就必须配齐对应的正向恢复/清理步骤：
    1. **主从 / 角色 / VIP 临时切换**：为了滚动重启、升级或补丁做了计划内切主（如 Patroni `switchover`、Redis `SENTINEL FAILOVER`、MySQL/MHA 切主、Keepalived 降优先级漂移 VIP）→ 原主重启追平（`Lag=0`）后，必须显式包含一步「切回原主库 / 恢复原 VIP 主节点」（若维护窗口紧张不愿二次闪断，可在 `risk_note` 注明可按需点击跳过）。
    2. **维护模式 / 自动高可用保护开关临时暂停**：如 `patronictl pause`（维护模式）、临时关闭 HA 自动切换或监控静默 → 变更完成后必须显式 `patronictl resume` 并核验已退出维护模式。
    3. **负载均衡临时摘流 / 降权**：如 HAProxy `set server ... state maint/drain`、Nginx 临时注释或降权 `upstream` 节点、ELB 临时摘除后端 → 变更完成后必须恢复 `ready` / 还原原权重并重载核验。
    4. **同步复制 / 限流 / 调试日志临时放宽**：如临时关闭同步提交（`synchronous_mode: false`）、临时下调 `synchronous_node_count` / `min-replicas-to-write`、临时开启 `log_statement=all` / `debug` 级日志或临时放宽 `pg_hba`/防火墙 → 完成后必须切回变更前严格策略与正常日志级别。
    5. **后台服务 / 定时任务临时停止**：如临时停掉了 `cron`、`systemd timer`、备份/归档任务或同步消费任务 → 验收前必须重新启动并确认恢复 `active`。
    6. **演练/验收临时脏数据与残留文件**：如测试读写或同步创建的临时库/表/测试写入记录、Redis 临时 Key、临时诊断账号/权限、`/tmp` 下的采集脚本或 `.bak`/`.tmp` 残留文件 → 验收后必须显式清理干净。
- **单框原子复制铁律（严禁多台滚动/破坏性操作塞进同一个命令复制框）**：
  - 工程师会直接点击命令框右上角「复制」把整块命令一次性粘贴进终端连续执行。
  - **绝对禁止**把多台节点的 `restart` / `reload` / `stop` / `switchover` / `failover` / 摘流操作，或“先看 `diff`/检查确认无误后再 `--apply`”写进同一个 `command` 代码块里！
  - 凡是中间需要人工确认恢复健康（如 `streaming`、`Lag=0`）后再推进下一台/下一段的操作，**必须**通过步骤的 `commands` 数组拆成多个**独立命令框**（每框独立复制、附带 `label` 与 `gate` 暂停核验提示），或者拆分为多条独立步骤。
- **堡垒机 / WebSSH 多行整块防吞行铁律（解决慢命令与 Ubuntu `sudo use_pty` 吞后续行）**：
  - 凡单框包含 **2 条及以上命令**（尤其含 `sudo`、`psql`、`patronictl`、`sleep`、`systemctl` 等耗时或会读 stdin 的命令），**必须**整块包裹在 `(\n...\n) </dev/null` 子 Shell 中，让交互式 bash 先完整解析全块再按序执行并关闭标准输入；**严禁**裸贴多行或使用 `bash <<'EOF'`（heredoc 走 stdin 仍会被 `sudo`/`psql`/`ssh` 吞掉后续行），也不要把多条耗时命令用 `;` 拼成超长单行。单条命令无需包裹。
- **每步必须独立可复制、执行机器一眼看懂**：严禁使用 `read -r -p` 交互式填变量、严禁跨步骤隐藏环境变量（如 `OLD`/`R1`/`R2`/`CFG`/`SCOPE` 或 `source /root/env`）、严禁在标题或执行位置里用晦涩代号；每步 `target_role` 必须明确写清要 SSH 登录哪台机器（如「所有数据节点（node-1 / node-2 / node-3，逐台登录执行）」「当前从库（先 node-2 再 node-3）」「当前主库（如 node-1）」「集群外客户端/跳板机，或非当前主库的从库节点（如 node-2 / node-3）」），不要假设现场必然存在独立的第 4 台跳板机。
- 每步执行后直接贴入终端输出或截图，由 AI 对照预期判据自动判定通过并回写实测结论；未通过时根据实际报错定位根因，通过 `replace`（原地修正命令）、`insert_before`（补充前置准备步骤）或 `retry`（现场环境修正后复测）迭代打磨，直至必测步骤全部通过。

## 第四步：定稿《生产变更实施方案》（finalized）
- 仅当测试环境必测步骤全部验证通过后，才允许定稿生产 SOP。
- 定稿文档必须把测试环境打磨通过的最终命令、AI/人工实测结论、注意事项与回退红线映射到第二步核实的生产真实节点与当前主从角色上，支持在集群「文档」页复核签字并导出标准 Word（`.docx`）。

## 在对话中拉起演练
- 在 AI 助手或交付对话中讨论已投产集群的变更需求时，先核实平台状态与基线配置，再直接调用 `propose_rehearsal` 工具生成「发起变更演练」卡片（在 `goal` 中写明变更诉求、约束与需在只读探针阶段核实的要点），让用户一键带入上下文进入「变更演练」工作台。
