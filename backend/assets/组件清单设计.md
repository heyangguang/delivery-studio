# 组件清单与部署规格设计（含 2.0 原生 Ansible 标准）

## 0. Kyndryl Delivery Studio 2.0 原生 Ansible 引擎与动态表单标准（现行推荐）

平台已全面演进为 **100% 原生 Ansible 2.0 架构**（`schema: studio/v2`），完全消除私有 `mw.*` DSL 锁定，支持直接导入并托管市面上任意标准 Ansible Role、Collection（`galaxy.yml`）、Playbook 工程仓库与单文件 Playbook YAML。

### 0.1 标准目录契约
- `delivery-studio.yaml`（可选，导入时可自动推导生成）：仅声明组件标题、分类、入口 Playbook（`deploy` / `verify` / `probe` / `cleanup`）、Inventory 分组（`groups`）与快捷架构方案（`schemes`）。
- `playbooks/deploy.yml`、`playbooks/verify.yml`、`playbooks/probe.yml`、`playbooks/cleanup.yml`：100% 标准 Ansible Playbook，脱离平台直接执行 `ansible-playbook -i inventory/hosts.yml playbooks/deploy.yml`。
- `roles/<role>/defaults/main.yml` 与 `roles/<role>/meta/argument_specs.yml`：所有可配参数的唯一事实源。

### 0.2 AST 自动动态表单协议（新增 Ansible 变量即自动生成表单）
经典交付页面（`#/new/<component>`）通过后端 AST 解析引擎实时将 Ansible 源码映射为交互式分组表单，**前端零硬编码**：
1. **自动提取与保序合并**：依次解析 `meta/argument_specs.yml`、`defaults/main.yml`（含行首/行尾 `#` 注释）、`group_vars/all.yml`、Playbook 顶层 `vars:`。
2. **智能控件推断**：`choices`→枚举下拉，`password`/`secret`/`no_log`→密文输入框+随机生成，`*_port`→端口（`1..65535`），`bool`→开关，`*cidr*`→CIDR 校验，`*_dir`/`*_path`/`*_file`→路径，`list`/`dict`→标签数组/JSON 块；自动推导 `s`/`ms`/`bytes` 单位。
3. **语义分组**：自动归入 `basic`（基础）、`network`（网络与端口）、`ha`（高可用与流量治理）、`security`（安全与凭据）、`tuning`（性能、存储与日志）、`baseline`（操作系统内核基线）。
4. **条件联动（`when:`）自动推导**：扫描模板 `{% if ... %}` 与任务 `when:`（取部署路径交集，跳过 `probe.yml`/`cleanup.yml`/`assert`/`debug`），自动生成前端实时显隐规则（如 `patroni_synchronous_mode == true`、`group.etcd == 0`、`nginx_proxy_mode == 'stream'`、`elb_mode == 'domain'`、`elb_health_check_type == 'http'`）。

### 0.3 全场景交付与治理闭环
- **离线交付（`offline`）**：生成 `<cluster>-ansible-v2.tar.gz`、`SHA256SUMS` 与交付手册；配置内网源时自动生成 `playbooks/configure-offline-repo.yml`。
- **自动编排（`automatic`）**：由执行中心 Linux 控制节点执行并流式回传脱敏日志，支持 `--check --diff` 真实配置差异预演（严格隔离不污染正式进度）及在线修订。
- **存量集群纳管（`#/import`）**：直接选用 2.0 组件或预设生成 100% 只读探针或执行 `playbooks/probe.yml` 采集现网基线并一键纳管。

## 1. 要解决的问题

- 应用逻辑写死在代码里：阶段在 `prepare.py`，手册在 `flexibleDocuments`，测试清单在 `dbTests`，前端另有一份。新增应用要同时改三处。
- 依赖是无条件的：单节点 PG 也会带 etcd。
- 入口层是 PG 的内置概念：只有 ELB，没有 haproxy、nginx、keepalived 的位置。
- 实施人员无法自己录入应用。
- 没有版本维度：同一应用的不同版本的包、参数、依赖差异无处表达。

## 2. 设计原则

1. **平台只做离线生成**：产出各机器安装包、手册、校验清单；不连接目标机。这一点不变。
2. **组件不关心部署在哪**：组件只声明"需要几个实例、能否和谁同机"，放在哪些机器由用户决定。
3. **依赖的是能力，不是具体软件**：PG 需要 `dcs`，不是 etcd。
4. **一份规格，两个视图**：表单和 YAML 是同一份数据的两种编辑方式，可互相导入导出。
5. **版本是一等公民**：规格里固定到具体版本，并锁定清单摘要，可复现。
6. **条件只写在数据里**：`when` 表达式由后端统一求值，前端不自己实现一份。

## 3. 四个对象

| 对象 | 谁写 | 内容 |
|---|---|---|
| 组件清单 `Component` | 开发者、实施人员 | 一个中间件的定义，含多个版本 |
| 部署规格 `Deployment` | 实施人员（表单或 YAML） | 某客户这一次的机器、组件实例、放置、参数、版本 |
| 方案模板 `Preset` | 开发者、实施人员 | 部署规格的预填值，例如"PG 单节点""PG 一主两从" |
| 交付产物 | 平台生成 | 节点包、手册、校验清单、版本锁 |

### 3.1 概念关系

```
Deployment
 ├─ hosts[]                  用户录入的机器池（IP、主机名、磁盘）
 ├─ instances[]              组件实例：pg-main(patroni-pg 17)、etcd-main(etcd 3.5)、lb-main(haproxy 2.8)…
 │    ├─ version             固定到具体版本
 │    ├─ params              按该版本的 schema 填写
 │    └─ placement           落在哪些 hosts 上，或 external
 └─ bindings[]               实例之间的连接：lb-main.frontend → pg-main.writer
```

## 4. 组件清单

### 4.1 结构

```yaml
schema: mwpack/v1
component: patroni-pg
title: PostgreSQL（Patroni 高可用）
category: 数据库
provides:
  - capability: sql-endpoint

versions:
  - id: "17"
    platforms: [ubuntu-24.04-amd64]  # 这个版本适用的操作系统
    packages:                        # 软件包写确切版本；文件由平台软件库提供（第 15 节）
      - {name: percona-postgresql-17, version: "2:17.11-1.noble"}
      - {name: percona-patroni, version: "1:4.1.5-1.noble", when: count(roles.replica) > 0}
  - id: "16"
    extends: "17"                    # 版本差异用覆盖表达，不复制整份
    packages:
      - {name: percona-postgresql-16, version: "..."}

roles:                               # 一个实例内的角色
  primary:  {min: 1, max: 1}
  replica:  {min: 0, max: 4}

requires:
  - capability: dcs
    when: "count(roles.primary) + count(roles.replica) > 1"
    default_impl: etcd
    placement: {default: same_hosts, allow: [same_hosts, dedicated]}

params: {}                           # 见 4.2
endpoints: {}                        # 见 4.3
lifecycle: {}                        # 见 4.4
tests: {}                            # 见 4.5
```

关键点：

- `requires.when` 为假时，etcd 不出现在角色、端口、阶段、手册任何一处。**单节点 PG 不带 etcd 是这一条规则的结果，而不是特例。**
- `placement.allow` 表达两种放法：etcd 和 PG 同机，或 etcd 单独三台（两个 PG 节点加三个 etcd 是常见需求）。默认值由模板给出，用户可改。
- 版本之间通过 `extends` 做覆盖，只写差异。

### 4.2 参数

JSON Schema 子集加界面提示。`since/until` 控制版本范围，`when` 控制显示与校验。

```yaml
params:
  replication:
    type: enum
    values: [async, quorum]
    default: async
    when: "count(roles.replica) > 0"          # 无从库时不显示、不校验
    ui: {group: 复制, label: 复制策略}
  sync_ack_count:
    type: int
    range: [1, "count(roles.replica)"]
    when: "params.replication == 'quorum'"
  tde:
    type: bool
    default: false
    since: "17"                              # 版本不支持则整项隐藏
secrets:                                     # 平台生成，不让用户填
  - {name: postgres_password, generate: token32}
```

### 4.2.1 数据流（flows）

组件可以声明自己的角色之间怎么流动数据，界面据此把部署画成带流动连线的图。它只用于展示，不影响生成：

```yaml
flows:
  - {id: wal, title: WAL 流复制, kind: replication, from: primary, to: replica, when: "count(roles.replica) > 0", sync: "params.replication == 'quorum'"}
  - {id: raft, title: Raft 共识, kind: mesh, from: member, to: member, sync: "true"}
```

`kind: replication` 是从 `from` 角色的机器到 `to` 角色的机器的单向流（带箭头）；`kind: mesh` 是同一角色的成员互相通信（`from` 与 `to` 必须相同）。`when` 为假（比如没有从库）时不画；`sync` 为真时标“同步”。负载均衡的入口到后端的线不用声明，由 `fronts` 自动画。平台代码里没有任何产品特例。

### 4.3 端点契约（负载均衡的接口）

组件只声明"我的后端长什么样"，不知道前面是什么 LB。

```yaml
endpoints:
  writer:
    protocol: tcp
    backends: "hosts(role=*):{params.pg_port}"
    health: {type: http, port: "{params.restapi_port}", path: /primary, expect_status: 200}
    lb: allowed                              # allowed | discouraged | none
  reader:
    protocol: tcp
    backends: "hosts(role=replica):{params.pg_port}"
    health: {type: http, port: "{params.restapi_port}", path: /replica, expect_status: 200}
    lb: allowed
```

不同组件的 `lb` 取值不同：

- PG、MySQL：`allowed`。
- Redis 哨兵模式：`discouraged`，因为客户端应走哨兵；用 LB 时需要 `tcp-script` 健康检查。
- Kafka：`none`，因为 advertised listeners 决定客户端直连，LB 会破坏它。

选了 `none` 的端点，表单里不显示"前端入口"。

### 4.4 生命周期

标准阶段固定：`preflight → install → configure → start → verify`，另有 `cleanup`。平台按 `requires` 做拓扑排序，生成跨组件的执行顺序。每个动作有三种实现方式，由简到繁：

- **L1 声明式步骤**：`package`、`template`、`file`、`systemd`、`wait_port`、`command`、`assert`。平台编译成 Ansible 任务。大多数无状态或简单服务（haproxy、nginx、keepalived、单机 Redis）只需这一档。
- **L2 Ansible role**：应用包自带 `roles/`，清单里引用。
- **L3 插件**：代码实现，仅用于拓扑逻辑很重的应用（现有 Patroni 的 `node.py`）。

每个步骤都带元数据，手册从这里渲染，不再拼字符串：

```yaml
lifecycle:
  configure:
    - id: render-haproxy-cfg
      title: 生成 haproxy 配置
      template: haproxy.cfg.j2
      dest: /etc/haproxy/haproxy.cfg
      effect: change                         # read-only | change | disruptive
      expect: "haproxy -c -f 校验通过"
```

### 4.4.1 回退（rollback，1.0.89-dev 起）

每个步骤可以写 `rollback:`，说明这一步之后出了问题怎么退回：具体命令、要恢复的文件，或者明确写「不可回退：……」及原因。手册和执行页在每个会改动机器的步骤下显示「出了问题怎么退回」；没写时显示「组件没有声明，先停下联系平台维护人员」，变更方案的向导也会提示有几个步骤没有声明。AI 解读方案时会按执行顺序说明哪一步之后还能退回。可以用 `${cluster}`、`${instance}`、`${params.<键>}`。

```yaml
    - id: join
      title: 新成员逐个加入集群
      rollback: "在任一原有成员上 etcdctl member remove <新成员 ID>，再停掉新机器上的 etcd 并清空 ${params.data_dir}。先移除成员再停服务。"
```

变更步骤（changes）一定要写，它们改的是正在运行的集群；只读步骤不用写。

### 4.5 测试

测试也是数据，`when` 取代现在的 `skip` 判断：

```yaml
tests:
  - id: switchover
    title: 计划切换
    when: "count(roles.replica) > 0"
    effect: disruptive
    needs_confirm: true
    run: {role: pg_test, action: switchover}
  - id: via-endpoint                         # 经 LB 连接，对所有 LB 实现通用
    scope: endpoint
    check: {type: sql, expect: writable}
```

### 4.5.1 运维知识（operations，1.0.80-dev 起）

`operations:` 写给集群交出去以后做日常运维的人，用在每个集群的「运维交接文档」里，不影响生成。平台把它按实例展开：`when` 为假的条目不出现（例如只有从库时才有的检查），命令里的 `${cluster}`、`${instance}`、`${params.<键>}` 换成这个实例的实际值。AI 起草交接文档时只在这些内容之上补充本集群特有的注意点，不改作者写的内容。

```yaml
operations:
  overview: 一段话：这个软件怎么工作、坏一台会怎样、日常最该关注什么
  checks:            # 日常巡检
    - {title: 成员健康, hosts: 任意一台成员, cmd: "etcdctl --endpoints=127.0.0.1:${params.client_port} endpoint health --cluster", expect: 每个成员都 is healthy}
    - {title: 复制延迟, when: count(roles.replica) > 0, cmd: ..., expect: ...}
  tasks:             # 常见操作
    - {title: 手动备份, cmd: ..., note: 注意事项}
  faults:            # 典型问题与排查
    - title: 一个成员宕机
      symptom: 看到的现象
      steps: [先确认什么, 再看什么, 什么情况要走平台方案]
      cmd: journalctl -u etcd -n 200 --no-pager
  logs:
    - {name: 服务日志, text: journalctl -u etcd}
```

写法要点：命令必须能直接复制执行；“正常”写可以判断的标准；排查步骤里涉及改变集群（加减成员、改配置）的，指向平台的方案，不要让人手工改。

### 4.5.2 升级路径（upgrade_from，1.0.82-dev 起）

版本可以写 `upgrade_from: ["16", "17.*"]`，表示运行中的集群可以从这些版本直接升到它。写了就严格执行：不在列表里的起点会被拒绝，并按已声明的路径提示分步（例如 14 → 15 → 16，每步一份升级方案）。没写时，同一大版本内直接放行；跨大版本给出警告，写进手册的“注意”，要求人工评估。任何情况下都不允许降级。

### 4.6 参数的两个层次：实例参数与附加项参数

同一个应用里有两类参数，不要混在一起：

| 层次 | 例子 | 属于谁 | 声明位置 |
|---|---|---|---|
| **实例参数** | PG 的 TDE、复制策略、`shared_buffers`、Patroni TTL、pgBackRest 保留数；nginx 的 worker 数；Redis 的持久化 | 整个实例 | `params` |
| **附加项参数** | PG 的 `pg_trgm`、`btree_gist`、`plpgsql`、`amcheck` 这些数据库扩展本身的选项与目标数据库 | 实例里的某个子对象（数据库） | `addons` |

TDE 是 PG 独有的特性，所以它是 `patroni-pg` 的实例参数，不是通用能力。组件是通用的，应用独有的东西放进该组件自己的 `params` 和 `addons`，不上升为平台概念。

附加项（Addon）是组件的可选增强，通用结构如下，不同应用各自填内容：

```yaml
addons:
  kind: pg-extension                 # 种类由组件自己命名；nginx 可以是 nginx-module，Redis 是 redis-module
  scope:                             # 附加项作用在实例内的哪类对象上
    name: database
    source: user-list                # 目标数据库由用户列出；平台不自动建库
    defaults: [postgres, template1]
  catalog:
    - id: pg_trgm
      contrib: true                  # 随主包提供，不需要额外制品
      install: {action: create-extension, name: pg_trgm}
    - id: btree_gist
      contrib: true
      install: {action: create-extension, name: btree_gist}
    - id: plpgsql
      contrib: true
      builtin: true                  # 通常已存在，选择后只确保可用
    - id: amcheck
      contrib: true
      install: {action: create-extension, name: amcheck}
    - id: some_third_party
      since: "17"
      packages: [{name: some-third-party-ext, version: "1.2"}]                # 第三方扩展的软件包同样从软件库取
      requires_params: {shared_preload_libraries: some_third_party}           # 反向写入实例参数
      restart: true                  # 需要重启实例，手册要标明会断连
      params:
        some_option: {type: int, default: 10, level: database}                # 扩展自己的参数
```

规则：

- **附加项参数有层级**：`level: instance` 写入实例配置（例如 GUC），`level: database` 在目标数据库内设置。表单里分开展示，附加项参数放在对应扩展的卡片下。
- **附加项可以反向要求实例参数**，如 `shared_preload_libraries`；平台把这种要求并入实例参数并在预览中标出"由扩展 xxx 引入"，用户不能把它改掉。
- **版本相关**：扩展可用性按组件版本过滤（`since/until`），第三方扩展还要与 PG 大版本匹配。
- **边界**：已存在的扩展保留，不自动升级、不删除；模板库（如 `template1`）里的扩展会被以后新建的数据库继承，手册里要提醒。这些沿用现有 [extensions.go](extensions.go) 的行为。
- **目标数据库必须已存在**，平台不自动建库；校验时只检查名称合法，是否存在由部署后的验证步骤确认。

附加项也是版本化数据：`versions[].addons` 可以覆盖目录，所以 PG 16 与 17 可用的扩展集可以不同。

## 6. 部署规格与放置自由

放置完全由用户决定，平台只做校验：

- 某角色实例数是否在 `min/max` 内。
- 是否违反该组件允许的 `placement`。
- 同机端口冲突。
- 磁盘与资源是否够用。
- 反亲和：要求落在不同机器上的角色是否分开。

### 6.1 例：同一个 PG 三种入口放法

**A. LB 放在新的两台机器，配 keepalived**（`mwdeploy/v1`，实际格式；`placement` 是“角色 → 机器”的映射）

```yaml
id: pg-prod
hosts:
  - {name: db-1, ip: 10.0.1.11, disk: /dev/vdb}
  - {name: db-2, ip: 10.0.1.12, disk: /dev/vdb}
  - {name: db-3, ip: 10.0.1.13, disk: /dev/vdb}
  - {name: lb-1, ip: 10.0.1.21}
  - {name: lb-2, ip: 10.0.1.22}
instances:
  - id: pg
    component: postgresql
    placement: {primary: [db-1], replica: [db-2, db-3]}
    params: {client_cidr: 10.0.1.0/24, tls: true, tde: true}
  - id: lb
    component: haproxy
    placement: {balancer: [lb-1, lb-2]}
    params: {ha: keepalived, vip: 10.0.1.100, vip_interface: eth0}
    binds:
      - {endpoint: pg.writer, listen: 5432}
```

没有写 etcd：`postgresql` 有从库时 `requires: dcs`，平台自动补 `pg-dcs`（etcd），放在与 pg 相同的机器上；要独立机器就把它写成显式实例，或在界面点“自行指定”。`ha: keepalived` 同理补出 `lb-vip`（keepalived），与 haproxy 同机。

**B. LB 与数据库同机**：`placement: {balancer: [db-1, db-2, db-3]}`，同机端口冲突由平台校验，数据库的 `pg_hba` 自动放通这些负载均衡机器（四层转发会让客户端看起来是负载均衡的地址）。

**C. 外部 ELB**：`component: external-lb`，没有 `placement`，不产出安装包，只在 `03-入口测试.md` 里给出“云平台配置表”（前端、域名、后端、健康检查）。

三种放法对 PG 实例的 `params` 和测试没有任何影响。绑定时平台会按端点声明检查：Nginx 无法做 HTTP 健康检查，所以不能代理 Patroni 的 `/primary`；`lb: none` 的端点（如 Kafka）不允许放在负载均衡之后。

### 6.2 版本锁

交付时平台写出 `deployment.lock.json`，记录每个实例的确切版本、清单内容摘要、所有制品的 sha256、所用平台版本。同一份 lock 可重新生成相同交付；变更版本即视为新交付。

## 7. 版本差异怎么表达

不同版本可以在以下方面不同，都写在该版本的覆盖里：

| 差异 | 例子 |
|---|---|
| 制品与平台 | PG 16 与 17 的包不同；某版本不支持 Ubuntu 24.04 |
| 参数 | 参数新增、删除、默认值变化（`since/until`） |
| 依赖 | **Kafka 3.3 前依赖 `zookeeper`，之后可用 KRaft，不再需要** |
| 角色 | KRaft 有 controller 角色，ZK 模式没有 |
| 生命周期与测试 | 某版本新增的验证项 |

Kafka 是检验这个模型的最好例子，需要在草案阶段就跑通：

```yaml
component: kafka
versions:
  - id: "3.5"
    requires: [{capability: zookeeper}]
    roles: {broker: {min: 1}}
  - id: "3.7"
    requires: []                              # KRaft
    roles:
      controller: {min: 1, max: 5}
      broker: {min: 1}
```

跨组件版本约束写在 `requires` 里：`{capability: dcs, version: ">=3.4"}`。求解器在规格里找到不满足的组合时，给出具体冲突，而不是静默选一个。

## 8. 表单、YAML、导入导出

- **规格 `Deployment`**：表单读写同一份 JSON/YAML。导出得到完整 YAML，导入后表单回填。导入时先做 schema 校验，再做依赖求解，错误按字段位置报告。
- **清单 `Component`**：同样支持表单和 YAML。L1 的清单可以完全用表单录入（制品、参数、步骤）。
- **表单由 schema 渲染**：前端不再为每个应用写页面。前端把当前填写的内容发给后端 `resolve` 接口，后端返回可见字段、校验错误、依赖展开后的实例列表和节点要求。这样 `when` 只在 Go 里实现一份。
- **清单生命周期**：`草稿 → 静态校验 → 空环境验证 → 已发布`。未发布的版本在商店里显示为"待验证"，只允许内部试生成，延续"没验证过的不能冒充可部署"的原则。

## 9. 生成侧如何变

当前每个应用一个生成器。改成一个通用管线：

1. 加载规格，解析清单，求解依赖和放置，得到**实例图**（含自动补出的 etcd、keepalived）。
2. 校验：schema、版本兼容、放置约束、端口冲突、证书。
3. 按放置给每台机器列出它承担的组件，只打入这些组件及版本的制品。
4. 渲染配置模板、Ansible 清单、阶段列表。
5. 从步骤和测试元数据渲染手册：免密配置、部署、功能测试、入口测试、清理。
6. 写 SHA256 清单和版本锁。

现有 Patroni 的 `node.py` 作为 L3 插件保留，先不重写。

## 10. 迁移顺序与验收

1. 定 `mwpack/v1` schema 与求解器，**不改行为**：把现有 PG 迁成清单（etcd 和 patroni-pg 两个组件）。验收：用现有 dev、standard、enhanced 三个方案，新旧管线生成物逐字节一致（除时间戳）。
2. 打开 `requires.when`，验收：单节点 PG 不再出现 etcd。
3. `l4-lb` 与 haproxy、nginx、keepalived、external 四个实现，验收：同一套经 LB 的测试在三种实现上都通过。
4. 通用手册与测试渲染器，替换 `flexibleDocuments`。
5. 第二、三个应用：Redis（哨兵）、etcd 独立部署，用来检验抽象。
6. Kafka（验证版本带来的依赖变化）、MySQL（验证 writer/reader 双端点）。
7. 规格与清单的表单和 YAML 导入导出；清单发布流程。

## 11. 范围外（先不做）

- 平台直接连接目标机执行。
- 多个应用跨规格的联合编排，如 PG 加 Redis 在一份规格里一起交付（schema 允许多个实例，界面先只支持一个主应用加其入口层）。
- 在线升级与扩缩容。
- Vault 和云 KMS。

## 12. 已确认的决策

1. **表达式语言**：`when` 等条件使用 Go 的 `expr-lang/expr`，允许引入依赖，随源码离线 vendor。
2. **模板语言**：L1 的配置模板使用 Jinja2，与 Ansible 一致，由 Ansible 在目标侧渲染。
3. **清单存放**：这里的"清单"指**组件定义本身**（应用有哪些版本、参数、步骤），不是用户下载的交付物。用户生成的交付物仍然是生成后在界面里下载，这一点不变。组件定义保存在服务器的数据目录里：`catalog/<组件>/<版本>/manifest.yaml` 加 `roles/`、`templates/`、`files/`。文件目录是唯一真相，数据库只存索引和发布状态，用于列表和检索。界面里的"导入/导出"就是把这个目录打包或解包，换服务器或做离线交接时直接拷贝即可。
4. **PG 特性的位置**：TDE、PITR、复制策略、备份策略等都是 `patroni-pg` 的实例参数，不拆成子组件。数据库扩展（`pg_trgm` 等）是附加项，见 4.6，它有自己的目标数据库和参数。**组件保持通用，应用独有的内容只出现在该组件自己的 `params` 与 `addons` 里。**

## 13. 沿用的执行、证据与清理原则

下列原则来自已删除的《部署自动化体系设计》《Ansible自动化实施方案》，其中的 Go 模块树、mwctl 新命令形态和 Ansible 工程目录已被本设计取代，下面只保留仍然有效的约束。新组件的生命周期、测试和清理步骤都必须遵守。

### 13.1 边界

- 平台负责安装配置、验收演练、测试产物生命周期和交接。上线后的日常备份使用原生工具（PG 用 pgBackRest）；定时计划、保留策略、备份介质由正式备份方案另行确定，部署和验收不擅自启用。
- 执行层是 Ansible。控制节点是用户选定的一台被管机器（现为 node01），被管节点不装 agent；SSH 公钥交换、主机公钥指纹核对、`StrictHostKeyChecking` 保持现有流程，不自动信任未知主机；Ansible 读取控制节点已有的 root 密钥，不把私钥复制到被管节点。
- 旧的 mwctl 执行记录（`/var/lib/mwctl/<cluster-id>`）只读兼容，不被新流程改写、挪动或删除；不再把 mwctl 扩展成第二套执行引擎。
- Ansible 不会自动带来业务层的幂等、主备判断、备份安全删除、恢复链验证和回滚，这些由各组件的 role 与验收实现。

### 13.2 离线引导

先检查 OS、架构、Python 版本和现有环境，再用已锁定的依赖闭包离线安装 Ansible；collections 固定版本并随包提供；运行时禁止访问 PyPI 或 Galaxy。引导完成后才做连通性检查，不能用 Ansible 自己解决"首次安装 Ansible"。

### 13.3 动作与状态

- 每个动作声明：稳定 ID、目标节点或实例、前置事实、命令、影响范围、超时、完成判据、重试语义、失败后的处置。**不能仅凭退出码 0、一次探测或固定 sleep 宣布通过。**
- 状态分为：未执行、运行中、通过、失败、不适用、证据不足。任务编排、节点动作和业务验收分开记录：主备切换成功不代表应用流量恢复，文件校验成功不代表恢复演练成功。
- 不支持的能力明确显示"不支持"，不做空实现或返回成功的占位。控制进程中断或连接丢失后标"待核实"，重新检查真实状态后才允许继续。
- 部署、切换、故障演练、恢复、清理是各自独立的执行入口；普通部署不顺带停服务或清仓库。
- 关键前置检查失败必须阻止相关变更；用 `serial`、`run_once`、`delegate_to`、`any_errors_fatal`、`block/rescue` 表达规则，不对关键任务 `ignore_errors` 后宣称成功；handler 的重启范围要明确，重跑不能意外重启整个集群。
- `--check/--diff` 只用于支持它们的模块和模板预览，不代表故障演练或删除后重建一定可行；破坏性操作前，先在受限的临时目录做真实的能力探测。

### 13.4 锁与重试

- 执行锁至少按集群；磁盘初始化、软件源这类共享主机资源增加主机级互斥。远端锁、日志、资源身份都带上组件类型、集群 ID、操作 ID、节点和实例。
- 重试前重新校验身份、拓扑、版本和上次已完成的动作；不默认回滚已完成节点，不在故障后自动盲目切回旧主库。"恢复已有的部分结果"和"重新执行"是两种动作；不依赖 Ansible 的 retry 文件判断哪些节点可以安全重跑。

### 13.5 机密

密码和私钥不进入公开配置、版本库或普通日志。敏感任务用 `no_log`，敏感模板关闭 diff，不把全部变量写进公开报告。Ansible Vault 只保护静态敏感变量，不代替运行权限、日志脱敏和解密口令管理。证书与私钥放受保护目录，目录 700、文件 600；制包后再次验证包内权限与内容。已有密钥保持身份，不因重新打包而重新生成。私钥只进入控制节点的包。

### 13.6 测试资源与清理

- 每个测试在创建资源时登记：类型、所有者、节点、实例或数据库、绝对路径或对象 ID、备份标签、创建轮次、创建前后证据、是否仍在使用、删除方法。清理按登记表执行；遇到未知对象则保留并报告。
- 删除流程固定为：生成清单 → 核对实际对象 → 验证删除后必需的重建能力 → 保留交接证据 → 受限删除 → 复核。SQL 表、原生备份集、实例进程、数据目录是不同资源，不共用一条递归删除规则；备份由原生工具删除，不直接删仓库内部文件。
- 目录删除前核对规范路径、资源身份、当前进程以及所有可见 namespace 的挂载引用，发现占用就保留并报告。运行中的生产数据目录、生产 WAL 目录和运行密钥永远不在测试清理范围内。
- 预检分三层：静态配置、连接与权限与角色、可执行能力。预检成功不等于操作一定成功，所以仍要记录部分完成的状态和修复入口。
- 两种明确的交接策略：（a）尚未上线且用户明确放弃测试恢复历史：清测试表、停止并清理测试实例、清理测试备份和仓库归档，保留配置与必要证据；（b）已有业务或需保留恢复历史：先按业务要求准备恢复点，用原生工具按依赖清理，**禁止**执行（a）的仓库重置。

### 13.7 日志与交付

- 错误直接显示节点名、IP、动作、原始错误摘要、本地可打开的日志位置和下一步，远端路径只作补充；日志脱敏，按组件、集群、执行编号归档。
- 报告区分"历史测试通过"与"当前测试数据已清理"，避免后续拿已删除的探针当前置条件。
- 交付验收至少包括：集群身份与实际拓扑、软件与证书版本、已通过项目及覆盖边界、保留与已删除的测试资源、当前备份状态、原生运维命令、端口与访问方式、恢复材料位置、未执行或待确定的事项。

### 14.2 与前文设计的差异

- 阶段是 `preflight → install → configure → start → provision → verify` 六段（新增 `provision`：TDE 密钥、扩展、业务账户、备份与归档、滚动重启）。
- 部署规格里 `placement` 是“角色 → 机器”的映射；组件实例的依赖用 `uses` 钉住，用 `binds` 把负载均衡绑到端点，没有单独的 `bindings` 段。
- 附加项目前由 `postgresql` 的 `addons` 声明，规格里用 `addons: [{id, databases}]` 选择；附加项自带的参数（4.6 节的 `params`/`set_params`）已能解析，但现有四个内置扩展都不需要。
- PG 的长流程验收（切换、故障接管、PITR、入口持续写入）仍是 Python 辅助脚本 `pgtest.py`（由原 `node.py` 的验收部分整理而来），由 Ansible 分发并调用；部署部分已全部改为原生 Ansible 任务。
- 清单存放：内置组件嵌入程序，自定义组件在 `components_dir`（默认 `<data_dir>/components`），数据库只记录目录快照。

### 14.3 尚未做

- **未在真实 Ubuntu 机器上执行过任何生成的部署**。生成物经过静态与渲染层面的验证，行为是否与原有三节点流程一致须在空集群上验证；所有组件版本因此标为 `verifying` 或 `draft`，界面和手册都会提示。
- **软件库里没有的软件包就不能生成**：库里备齐什么由准备软件库时决定（第 15 节）。RedHat 系（el9）目前只准备了 HAProxy、Nginx、keepalived 的软件包，而且还没有 el9 的 Ansible 运行环境，所以它在“软件库”页可见、在向导里不可选。
- Redis、Kafka、MySQL 的组件尚未编写（模型已按它们的需要设计，Kafka 的版本依赖变化见第 7 节）。
- 组件工作台（第 16 节）只证明“生成的脚本结构正确”，不证明脚本在真实机器上跑得通；版本 `status` 仍由人在空环境验证后手工改为 `published`。
- 不支持把多个应用写在同一份规格里联合编排之外的场景（规格允许多个实例，但向导按“一个主应用 + 入口层”设计）。
- 成员变更、扩缩容、升级。

## 15. 软件包与软件库（2026-10-24 重做）

原先由人提供一个 `offline-repo.tar.gz`、清单里按文件名引用它，已废弃。现在平台自己知道软件从哪里来，交付里的离线仓库由平台按需拼出。

### 15.1 模型

- **清单只写“要什么”**：`packages: [{name, version, platforms?, when?}]`，版本必须是确切版本（交付要能原样重现）；`platforms` 缺省为该版本的全部系统。不同系统的包名和版本不同时，用 `platforms` 分行写（如 `nginx` 在 Ubuntu 是 `libnginx-mod-stream`，在 el9 是 `nginx-mod-stream`）。`artifacts` 只剩普通文件（`kind: file`），再写 `apt-repo` 会被校验拒绝。
- **操作系统（platform）**：部署规格里的 `platform` 字段，缺省为 `ubuntu-24.04-amd64`。目前登记两个：`ubuntu-24.04-amd64`（apt）和 `el9-amd64`（rpm，RHEL / Rocky / Alma 9）。要加系统，先在 `mwpack/platforms.go` 登记、在软件源里写好源，再用容器验证。
- **软件源（Source）**：每个系统有一份软件源列表，内置在 `pkglib/sources.yaml`（Ubuntu 官方源、Percona PPG 17、Rocky 9 BaseOS/AppStream），签名密钥随平台发布（Percona 密钥指纹 `4D1B B29D 63D9 8E42 2B21 13B1 9334 A25F 8507 EFA5`）。管理员可在“软件库 → 软件源”里按 id 覆盖（例如换成内网镜像）、停用或新增；获取软件包时始终验证签名，没有密钥的源不被接受。
- **软件库（Library）**：每个“系统 + 软件包@版本”对应一份**依赖闭包**（它自己加上目标系统干净安装里没有的依赖）、对应的文件（按内容去重，哈希校验）和仓库索引所需的元数据。闭包只在**准备软件库**时解析一次。

### 15.2 两个阶段

1. **准备软件库（需要 Docker 和网络，不在生成交付的路径上）**：在目标系统的容器里（`ubuntu:24.04`、`rockylinux:9`）按软件源配置解析依赖并下载；apt 每个软件包从空缓存开始解析，保证每份闭包单独可用；rpm 下载后用 `rpmkeys --checksig` 逐个验签。入口：界面“软件库 → 获取软件包”，或命令行 `library fetch`、`library fetch-all`（把所有内置组件需要的包一次备齐）。
2. **生成交付（不需要 Docker、不需要网络）**：把本次部署用到的软件包的闭包取并集，拼成离线仓库 `packages-<系统>.tar.gz`（apt 生成 `Packages`/`Release`，rpm 生成 `repodata`；只用库里存的元数据，不调用任何包管理器工具）。拼装是确定性的：同样的软件包集合得到同样的哈希，并按内容缓存。

### 15.3 联网与离线

- **能联网**：界面能查询软件源现在提供的版本（`apt-cache madison` / `dnf repoquery --showduplicates`），挑选后一键获取，所以能列出的版本比库里已有的更多。
- **不能联网（平台服务器通常如此）**：随平台发布时就带着准备好的软件库；需要新软件包时，在联网机器上用同一个程序 `library fetch` 获取、`library export` 导出为 `.tar.gz`，带回平台在“软件库”页导入。导入逐文件核对哈希，任何一项不符整包拒绝，路径穿越、未知系统、同名不同内容都拒绝。
- 平台服务器没有 Docker 时，“获取”按钮不可用并说明原因，其余（查看、导入、导出、生成交付）都不受影响。

### 15.3.1 软件源索引：搜索、预览、一键缓存（2026-10-24，apt 系统）

原先“查版本、算依赖”每次都要起一个目标系统的容器，慢，而且必须有 Docker。现在 apt 系统（Ubuntu）改成直接读软件源的**已签名索引**：

1. **更新索引（联网一次，约 25 MB、不到一分钟）**：下载每个源每个 suite 的 `InRelease`，用该源的密钥验证签名；再下载各 component 的 `Packages.gz`，核对签名清单里的大小和 SHA256，才存到 `<库>/index/<系统>/`。没有变化的文件不重复下载。Ubuntu（noble、updates、security）加 Percona 共约 9.8 万个软件包版本。
2. **搜索与查版本是内存里的操作**：服务启动和更新后把索引预加载进内存，搜名称（精确、前缀、包含）再搜描述，几百毫秒内返回，列出每个软件包的全部版本、来自哪个 suite。
3. **依赖预览**：选一个版本，立刻算出它在“干净的目标系统”上要装的全部依赖（只看 `Depends`/`Pre-Depends`，不装推荐包；已经在基础系统里的不算；基础系统清单 `pkglib/base/*.tsv` 来自该系统容器镜像的 `dpkg-query`），显示每个包的大小、为什么需要、库里是否已有、要下载多少。依赖找不全时明确列出缺的，不允许下载。
4. **下载到本地**：管理员确认后按预览的清单下载，每个文件核对已签名索引里的大小与 SHA256，再按与容器方式完全相同的格式入库（同样的文件名、哈希和元数据），所以交付生成、导出导入都不变。入库的就是本地缓存，导出后可带到内网的平台导入，部署时不需要联网。
5. **正确性依据**：对库里已有的 13 个由容器 apt 算出的闭包，用索引解析得到的文件集合**逐个完全一致**；直接下载入库的文件名、大小、SHA256 和影响安装的控制字段与容器方式一致（索引里只有一行简短描述、分类字段可能被软件源覆盖，这两项不同）。对照测试需要联网，设 `MW_NET_TEST=<软件库目录>` 运行 `go test ./pkglib`。
6. **外网建库、内网使用（两个平台配合）**：在能联网的平台更新索引、下载需要的软件包，然后“导出索引”（`source-index-<系统>-<日期>.tar.gz`，含已签名的发布清单与各 `Packages.gz`）和“导出全部”（软件包）；带到不能联网的内网平台，分别“导入索引”和“导入”软件包。之后内网平台**不联网**也能搜软件包、查所有版本、预览依赖，并看到哪些已在库；编辑不同的部署版本、产出部署手册本来就不需要网络。想看到新版本时，在外网平台重新更新并导出索引，再导入内网（只传变化也行，没有变化的文件不会重新下载）。
7. **索引包不被信任，导入时重新验证**：包里带着已签名的 `InRelease`，导入平台用**自己**的软件源密钥重新验签、逐个核对 `Packages.gz` 的大小与 SHA256，来自本平台没有的软件源、签名不对、文件被改、不是该系统的索引都拒绝；比本机现有的更旧的索引也拒绝（防回退）。离线测试（本地签名的假软件源）覆盖更新、导出、导入和各种篡改。命令行：`library index-update | index-export --out 文件 | index-import 文件`。
8. **RedHat 系 9 同样不用容器**（2026-10-25）：每个软件源下载 `repodata/repomd.xml` 和它的独立签名 `repomd.xml.asc`，用该源的密钥验签（Rocky 用 `RPM-GPG-KEY-Rocky-9`，即 Release key 2022），再按签名清单里的 SHA256 校验 `primary.xml.gz`；下载的每个 rpm 按 primary 里的 SHA256 与大小校验。`filelists`/`other` 只在下载软件包时按签名清单取一次并缓存（拼离线仓库要用）。BaseOS + AppStream 约 1.4 万个软件包版本，更新约一分钟。
   - 依赖解析按 dnf 的做法：只看 Requires（不装弱依赖）；文件依赖（如 `/bin/sh`）由 primary 里列出的文件和基础系统的文件满足；支持 `(A or B)`、`(A if B)`、`and`/`with`/`unless` 组合依赖，`or` 取第一个真正装得上的；多个提供者时优先与依赖方同源（同一个源码包）的那个，再取名字短的；替换了系统自带的包（如 `openssl-libs`）后，若系统自带的其他包（如 `openssl`）要求旧版本，就一起升级。基础系统清单 `pkglib/base/el9-amd64.tsv`（包、版本、提供、依赖）和 `el9-amd64.files.gz`（文件）取自 `rockylinux:9` 镜像。
   - 验证：库里 4 个由容器 dnf 算出的闭包（haproxy、keepalived 84 个文件、nginx、nginx-mod-stream）逐个完全一致；直接下载的文件名、大小、SHA256 与容器方式一致；拼出的离线仓库在**断网**的 `rockylinux:9` 容器里装上 haproxy。索引同样可导出、导入（导入时用本平台的密钥重新验签，拒绝更旧的 repomd）。离线测试用本地签名的假仓库覆盖文件依赖、组合依赖、同源优先、连带升级、导出导入与篡改。
   - 容器代码只留给 `library verify`（在断网容器里装一遍，作为独立校验）和对照测试，平台本身不再需要 Docker。

### 15.4 检查点

向导和生成接口在解析规格后还会检查两件规格之外的事：库里是否有这些软件包（缺什么、写明 `名称=版本`），以及所选系统是否有 Ansible 运行环境（控制节点要离线安装 Ansible，运行环境按系统各一份）。有任何一项不满足就不能生成，并指向“软件库”页。目录里每个组件版本按系统显示覆盖状态：可生成 / 缺 N 个包 / 无运行环境。

### 15.5 已验证与未验证

- 已用真实容器验证：Ubuntu 24.04 与 Rocky 9 上联网获取并验签、入库、拼装，然后在**断网**的干净容器里只用拼出的仓库安装成功；每个软件包都单独验证过它自己的闭包。
- **未验证**：RedHat 系上的任何部署（SELinux 对非标准监听端口的限制尚未处理；el9 没有 Ansible 运行环境，需要另外准备，Ansible 2.20 控制端需要 Python 3.12）；PG、etcd 组件只准备了 Ubuntu 24.04。

## 16. 组件工作台（2026-10-25）

组件不再只能靠“导出、改文件、再导入”维护。管理员在“组件”页进入**工作台**，对一份**草稿**用表单、文件和源码编辑，检查、试生成，满意后**发布**为新的修订；发布之前不影响任何交付。

### 16.1 存放与流程

```
<components_dir>/<名>/                 已发布（交付由它生成；与内置同名即覆盖内置）
<components_dir>/.work/<名>/           草稿：meta.json + files/
<components_dir>/.history/<名>/<0001>/ 修订：meta.json（时间、人、说明、增删改数）+ files/
```

- 以点开头的目录会被载入器跳过，所以草稿与历史不会被当成组件。草稿、已发布内容和修订都是同一种“文件集合”：`component.yaml`、`roles/`、`templates/`、`files/`。单文件 512 KiB、400 个、总 8 MiB（与导入包相同的上限与路径规则）。
- **内置组件不原地改**：“新建版本（覆盖内置）”从内置原样复制出草稿，发布后成为同名自定义包，覆盖内置；“恢复内置”删除它（历史修订保留）。“复制为自定义组件”用新名字复制一份（角色目录若与原组件同名一并改名，清单里的 `run.role` 同步改）。
- 发布 = 先完整检查（有错误不能发布）→ 原子换目录并热加载（失败自动回退）→ 记一条修订。**第一次通过工作台发布时，发布前的内容先存为修订 1**，所以总有东西可以回到。回滚 = 把某个修订放进草稿再发布，历史只增不改。草稿记录它开始时的已发布修订号，发布时若已变化会拒绝，除非明确选择覆盖。草稿保存带 `if_updated`，别处已保存过则 409，不会互相覆盖。
- 导入组件包也记一条修订（说明“导入”）。删除自定义组件连同草稿与历史一并删除。
- 权限暂不细分：只有管理员能写；操作员看不到工作台入口。

### 16.2 编辑界面

页签：概览、版本、参数、角色与关系、入口与密钥、部署步骤、测试与清理、文件、源码。

- **清单是唯一的真相，表单和源码同步**：表单用 `yaml` 库的 Document 修改，只动被改到的节点，注释、顺序和 `- {key: a, label: b}` 这样的行内写法原样保留（用 `flowCollectionPadding: false` 后，6 个内置组件解析再输出与原文逐字节相同）。源码页签是 CodeMirror，表单和源码任一边改都立即反映到另一边。
- “角色与关系”“参数”“入口”“步骤”“测试”页签顶部有**作用范围**：全部版本（基础）或某一版本的追加。版本里写的条目按 key/id 覆盖基础里的（沿用 `extends` 语义）。
- 表达式字段（`when`、`rules`、`default: =…`）旁有“可用变量”，按这个组件自己的参数和角色列出，点一下插入。
- **步骤**两种写法：运行角色任务文件（选角色目录、选任务文件，不存在时引导去创建），或“直接写任务”（模块选择 + 每个常用模块的参数表单，其余模块给 YAML 小编辑器；只允许 `ansible.builtin` 的安全模块，规则与导入时一致）。
- **版本的软件包**可直接“从软件库选择”：搜索用的是软件源索引（不联网），选版本即填入名称与版本号；选已有同名包会改它的版本。
- **文件**页签：文件树 + 编辑器（YAML、Jinja2、shell、Python 高亮，错误行标记，Ctrl/⌘+S 保存），可新建（任务文件 / 配置模板 / 静态文件 / 默认变量，带起始内容）、重命名、删除；“变量速查”是编辑器上的一块面板（可筛选，点一行复制 `{{ … }}`），按该组件的参数、角色、密钥列出可用的 `mw.*`、`mw_hosts`、`mw_cluster` 等；`.j2` 模板可**渲染预览**（用样例机器与默认参数，让 Ansible 的 `template` 真的渲染一遍，不运行 lookup）。
- 保存是自动的（改动 0.8 秒后写入草稿），页头显示“已保存/保存中/有未保存的修改”，离开页面前会补存。

### 16.3 检查与试生成

- **检查**（保存后自动运行，也可点页头）：每个 YAML 的语法与行号；清单解析与全部静态校验，问题按清单里的位置标到行；步骤指向的任务文件是否存在（报在那一步上）；任务里 `src` 的模板是否存在；`.j2` 的 `{{ }}`/`{% %}` 配对和 if/for 块配对；软件包版本是否还是模板占位符（错误）、是否已在软件库（警告）；`lookup` 的警告。页签上带红点数字，点问题跳到文件行。
- **试生成**：按草稿造一个样例部署（版本、方案、系统可选；每个角色按方案或默认台数摆放到 host1…，互斥角色各占一台），用 `Solve` + `Render` 走与真实交付完全相同的路径，不碰任何机器。给出：概览（样例、生成了多少文件和步骤、提示）、拓扑图（沿用部署图，数据流在内）、步骤列表、手册、**文件与差异**（与已发布版本用同一份样例生成的结果逐文件对照）、以及 **Ansible 检查**。
- **Ansible 检查**需要服务器上有 ansible-core（配置 `ansible_bin`，或环境变量 `MW_ANSIBLE_BIN`，或 `<data_dir>/ansible/bin`，或 PATH）：对每个生成的 playbook 执行 `ansible-playbook --syntax-check`。没有就如实显示“无法检查”及原因，其余照常。运行时只传最小环境，不带服务的数据库地址等机密，所有产物写在临时目录内，30–60 秒超时。
- 试生成在内存里载入草稿（`fstest.MapFS`），不写盘；这点很重要：早期实现用临时目录载入，目录一删角色文件就读不到，预览会悄悄丢掉整个角色。
- 局限（界面也这么说）：这些只证明**生成物结构正确**，不证明脚本在真实机器上能跑通；`--syntax-check` 不检查模板里变量是否存在，渲染预览才会。

### 16.4 模板与指南

- “新建”提供三种骨架：**单进程服务**、**主从**、**对等集群**。填组件名、显示名、软件包名、服务名、端口，得到一个能走完整个流程的最小组件（装包 → 写配置 → 起服务 → 查端口；主从的模板按角色写 `replicaof`，集群的模板列出全部成员），软件包版本是占位符，必须到“版本”页换成软件库里真实的版本才能发布。
- “怎么编写和修改组件”指南页（`#/components/guide`）：组件由哪几部分组成、谁写什么、角色任务文件是什么（用 etcd 的真实片段）、验证怎么做、修改的流程，以及三篇教程（改一个默认值、给 etcd 加版本、做一个 Redis 风格的新组件）。教程一在浏览器里按文字走过一遍：改 `heartbeat_interval` 默认值后，试生成的差异正是 `group_vars/all.yml` 与 `plan.json` 里 100 → 200。

### 16.5 接口

`GET /api/components/{name}/workspace`、`/draft`（GET 读 / POST 开始 `{from: live|builtin|revision, rev}` / PUT 保存 `{files, rename, if_updated}` / DELETE 放弃）、`/draft/{check|preview|diff|render|publish}`、`/revisions`、`/revisions/{n}`（与上一修订的差异）、`/revisions/{n}/restore`、`/fork`；`POST /api/components/new`（模板）、`GET /api/components/templates`、`GET /api/components/ansible`。都只给管理员。

### 16.6 未做 / 局限

- 草稿是每个组件一份、管理员共享；没有多人同时编辑的合并（有冲突检测，没有合并）。
- 没有二进制文件上传（`files/` 里已有的二进制文件会保留并列出，但不能在界面里新增）。
- 表单覆盖清单的全部字段，只有 `addons` 与 `lb` 这两段结构复杂、使用很少的内容用 YAML 小编辑器。
- 版本状态（`draft → verifying → published`）仍由人手工改；没有“在空环境验证通过后自动升级”的流程。

### 16.7 标识：图标与颜色（2026-10-25）

清单顶层可写 `icon` 与 `color`，界面里的组件图标、应用页横幅配色都由它决定；不写就按分类取默认。图标有 18 个（`database kv cache queue storage search balance gateway vip cloud server cluster monitor key container network file bell`），颜色 9 个（`indigo blue teal green amber coral red pink slate`），名字不在表里校验报错。两份名单分别在 `mwpack.ComponentIcons/ComponentColors` 与 `frontend/src/glyphs.tsx`，有测试（`glyphs_test.go`）保证一致。内置组件各有自己的图标（etcd 键值、HAProxy 分流、Nginx 网关、keepalived 盾牌脉搏、外部负载均衡 云、PostgreSQL 数据库）。新建组件时按所选结构给一个建议值，可在弹窗里改；之后在工作台“概览”的“标识”里改。目录接口把 `icon`、`color` 和默认版本的 `flows` 一并给出。

### 16.8 几处易错的细节（2026-10-25）

- **错误不只在 YAML 里**：每个表单页签顶部列出属于这一页的全部检查结果（含路径和“源码第 N 行”），点检查抽屉里的问题会跳到对应表单页签并展开出错的条目；发布对话框里错误会逐条写出来而不是只写个数。
- **“部署方式”**：概览页三张卡片——“托管部署”（平台直接连接集群安装维护，**即将支持**，现在不可选）、“离线部署”（默认：离线材料加安装步骤手册，现场人员执行）、“只出配置”（`kind: external`，如云负载均衡、硬件 F5：不装到机器上，只生成要在它上面配置的清单）。它问的是“这个组件怎么交付”，和是否离线无关：平台从不连机器，现在所有交付都是离线材料加手册。**“只出配置”的组件仍然可以写部署步骤**：它们被保留但不会出现在交付里（求解器对 external 实例本来就不生成步骤），切回“离线部署”就恢复使用，所以校验不再拒绝，工作台只在“部署步骤”页顶部提示。
- **改表单不改变文件版式**：短的纯值列表保持 `[a, b]` 一行写法；已有的开关关掉时保留 `key: false` 而不是删除再追加；新增的顶层键按固定顺序插入到合适位置（`kind` 在 `tags` 后，`icon/color` 在 `category` 后），不会堆到文件末尾。差异里只剩真正的修改。

### 16.9 试生成的样例可以自己摆（2026-10-25）

默认的样例仍然自动摆放（按方案或各角色默认台数，互斥角色各占一台），但“调整样例”可以改：**机器数**（1–12，host1…hostN）、**角色放在哪几台**（角色×机器的勾选表，实时显示每个角色的台数是否满足 min–max）、**改哪些参数**（枚举/开关给选择，其余自由输入，不改的用默认）。接口 `draft/preview` 增加 `hosts`、`placement`、`params`，返回里带上这个版本的 `roles` 与 `params` 供界面使用；机器名只能是 `host1`…`host99`。必填又没有默认值的参数，自动样例会按类型编一个无害的值（cidr、ip、端口、枚举第一项、能匹配 `pattern` 的值、域名形式的文本），否则 PostgreSQL、keepalived、外部负载均衡这类组件一试生成就会被“不能为空”挡住；`TestPreviewWorksForEveryBuiltin` 保证全部内置组件的自动样例都能生成。

### 16.10 常见中间件图标（2026-10-25）

图标库在通用的 18 个之外增加了 12 个常见中间件的图标（Redis、MySQL、Kafka、MongoDB、RabbitMQ、Elasticsearch、ZooKeeper、MinIO、Prometheus、Grafana、Kubernetes、Docker），是按各自特征画的同风格线条图标，不使用商标图形；选择器里分“通用”和“常见中间件”两组。灰色只用来表示“暂不可用/未正式发布”：没有分类默认的组件得到靛蓝，不再是灰色；外部负载均衡用琥珀色的云。

### 16.11 升级、补丁、扩缩容的步骤 `changes`（2026-10-25）

用户可以基于已有交付生成升级、补丁、扩容、缩容方案。平台不连接集群，所以怎么做由组件说明：`component.yaml`（或某个版本）里的可选 `changes:`，键是操作 `upgrade / member-add / reconfigure / member-remove`，值是步骤列表，写法与 `lifecycle` 相同（`id`、`title`、`effect`、`hosts`、`serial`、`when`、`run` 或 `tasks`……）。

- 机器选择多四种，只能用在 `changes` 里：`added:<角色>` 本次新加入、`existing:<角色>` 变更前就在、`removed:<角色>` 本次离开、`first-existing:<角色>` 变更前的第一台。
- 任务里可用 `mw.change.ops`、`mw.change.from_version`、`mw.change.existing.<角色>`、`mw.change.added.<角色>`、`mw.change.removed.<角色>`（元素带 `name`、`ip`）。离开的机器在清单里（分组 `<实例>__<角色>__removed`），其 IP 也在 `mw_hosts`。
- 没有写的操作，用户做这种变更会被拒绝。`extends` 的版本按操作合并，规则同其他步骤。
- 平台自己负责的部分不用写：只读核对机器与现状、软件源、密码文件、最后的只读复核（取 `lifecycle.verify`）与功能测试。
- 规格里的 `pins`（实例 → 软件包 → 版本）固定组件声明的软件包版本，用于修复交付；`change` 由服务器填写，用户提交的会被忽略。
- 工作台「步骤」页签下半部分是「变更交付的步骤」，四个操作各一组，机器选择里有上面四种。
- 原则：一次只动一个成员，动完确认健康再继续；不删除数据。


## 17. 步骤独立性标准

部署、变更、验收和清理都按独立步骤生成。ID 固定，文件名不随顺序改变；阶段仍能整段执行，但日志和结果分别对应子步骤。plan.json 的 step_format 为 2，sources 保存每一步引用的源文件、哈希和共享标记。

源文件默认归属于一个步骤。多个步骤引用同一任务、脚本或模板时，必须拆开，或者在组件顶层 shared_files 中用精确的文件路径声明公共依赖。不能使用通配符；不存在、越界或未声明的共享文件会阻止校验和生成。工作台“部署步骤”的“步骤独立性与公共依赖”区域可以选择这些文件。

新增组件优先采用一项业务动作一个任务文件、一个脚本入口和独立模板。不要用一个大脚本加动作参数容纳全部验收。公共模块只能放真正共用的能力，修改它会影响所有使用者；不能为了通过检查把所有文件都标成共享。

新交付使用完整的步骤路径匹配日志，避免同名步骤串记录。整阶段执行时同时生成阶段日志与子步骤日志；未执行的步骤不自动标记成功。旧交付继续使用旧记录格式。

具体规则、验证范围与尚未覆盖的运行隔离边界见项目中的《组件步骤标准.md》。源文件检查不是任意脚本的安全沙箱，不能据此承诺命令不会读取声明之外的远端状态。

### 17.1 输入与结果契约

步骤 inputs 是名称到 {type, value} 的映射。支持 string/int/bool/list/map，通过 mw_step_inputs 读取。框架在业务代码执行前检查类型。preconditions 和 postconditions 接受不带模板分隔符的 Ansible 表达式列表；分别在执行前、执行后断言，失败不能记为成功。工作台步骤编辑器可编辑这三项。

日志的 STEP_RESULT 使用 mwstep-result/v1，统一记录步骤路径、状态与结束时间；日志导入校验身份和结果一致性。shared_files 的文件内容版本仍由 sources 中的 SHA256 标识。

### 固定方案与独立管理组件

通过 presets 选择常见架构，方案字段必须显式记录在新交付中。companions 按条件创建管理组件，context 指向其管理的依赖能力；平台验证相同角色节点、有效的父方案及唯一管理者。管理器在部署步骤中使用 mw 访问父组件身份、参数、证书和入口，使用 mw_manager 访问自身依赖及软件包，禁止混合两份上下文。

PG 提供 single / replication / patroni。replication 是原生异步流复制，支持一主一从或多从，不提供自动故障切换；Patroni 独立管理高可用并依赖平台新建并管理的 etcd。未指定 deployment_mode 的历史规格保持 legacy 语义。方案之间不是在线迁移操作；不支持的升级、扩缩容或配置操作应拒绝生成，不套用 legacy 的流程。


### 面向用户的方案名称
使用能力名称而非技术组件名作为方案标题：基础系列（单节点）、主从系列（原生复制、人工切换）、高可用系列（自动故障切换）；真正提供数据分片时才使用“分片集群系列”。PostgreSQL 统一显示「单机方案」「原生主从方案」「Patroni 主从方案」，对应 single / replication / patroni，内部 ID 和 basic/replication/ha 能力契约保持不变；架构名称不能用“高可用”代替实现方式。Redis 等其他组件遵循同一命名原则，但只展示实际实现并验证的方案，不能因为多节点就承诺分片或自动切换。卡片说明必须写明节点结构、切换方式和适用限制；不要照搬云产品的存储分离、备节点不可访问等未实现能力。

## 18. 系列契约（界面、AI 与生成器共用）

每个 detail.presets[] 的 contract 声明真实能力。现有无契约清单保留读取兼容；工作台检查与发布要求所有展示方案补齐契约，强制发布不能跳过错误。组件骨架保留未完成项，不伪造高可用机制。

示例：series: replication；when: params.deployment_mode == 'replication'；failover: manual；mechanism: PostgreSQL 原生异步流复制；read_access: 主库读写，从库只读；sharding: false；limitations: [人工切换前必须隔离旧主]；acceptance: [postgresql/native-replication]；operations: [deploy]。

系列枚举：basic 基础系列（单节点、无切换、不分片）；replication 主从系列（多个节点、人工切换、不分片）；ha 高可用系列（多个节点、自动切换、不分片）；sharded 分片集群系列（多个节点且明确分片）。展示名称可追加“ · 规格”。这些分类不能替代中间件自身的角色、节点数量、依赖和参数校验。

when 用于运行时识别方案，预设自身必须匹配，同一部署不允许匹配多个系列。验收引用必须存在并有 expect；本组件测试必须在各支持版本的该方案中启用。支持的变更操作必须在对应版本有适用步骤；声明为空不能被解释成“全部支持”。集群操作菜单和变更生成器读取契约限制，AI 工具直接返回契约内容。

此门禁验证声明的一致性与可执行入口，不能证明脚本真实完成自动故障切换。组件仍须执行真实环境验收，通过后才可变更其验证状态。

可独立部署的组件发布时必须至少提供一个带契约的方案，删除全部 presets 不能绕过要求。kind: external 的外部连接组件和声明 context 的管理组件不提供独立系列，随父方案使用。现有内置 PG、Redis、etcd、Nginx、HAProxy、keepalived 已纳入契约；依赖管理、版本和步骤隔离仍由原有规则共同约束。

## 19 多文件清单与方案表单

component.yaml 是组件唯一入口，使用 {$file: manifest/...yaml} 引用独立 YAML 文件。引用映射只能含 $file；路径相对组件根目录，只允许 manifest/ 下 .yaml 文件，不允许路径回退、循环引用、重复归属和 YAML 别名。每个文件一个 YAML 文档。

- 公共参数、角色、版本等写入 manifest/common/；每个部署方案写入 manifest/schemes/<稳定ID>.yaml；生命周期和变更阶段写入 manifest/actions/，测试和清理各步骤独立成文件。
- 一个中间件仍是一个组件，方案共享公共定义，不复制成三个组件。界面部署方案标签每次仅编辑一个方案；切换方案同步节点、角色、参数和条件依赖。基础系列只保留其需要的节点；其他组件实际占用的节点不能误删，已填写地址的移除须确认。
- 修改前读取入口并沿 $file 找到实际所属文件，只修改所属片段。不要把分片重新内联到 component.yaml，不要为小改动重写全部清单。新增方案同时提交片段和入口引用；引用文件与入口必须一起通过 run_check。
- 文件拆分只改变存储组织，不代表步骤实现独立。仍须遵守第17章私有实现、精确共享依赖和输入契约，验证修改A不影响B/C。
- 旧单文件清单仍可读取；禁止覆盖已有草稿或自动改变历史交付。迁移必须验证展开后语义一致、各方案预览和同步影响范围。


## 20. 交付能力、自动执行与报告

组件顶层 delivery_modes 是可多选列表：offline（离线部署）、automatic（自动执行）、configuration（仅出配置）。旧软件组件缺省为 offline，旧外部配置组件缺省为 configuration；平台升级不自动给旧组件授予自动执行能力。工作台的概览及发布窗口都可选择，后端发布校验不能绕过。

声明 automatic 时，每个版本的生命周期、变更、测试、清理步骤都必须声明 timeout（1–86400秒）、非空 postconditions 和 expect。postconditions 是真正执行的 Ansible 断言，必须验证本步骤产生的结果，不能用 true 等常量凑数。inputs.timeout 只是传给业务任务的输入，不能替代步骤顶层 timeout。步骤表单可填写这些字段；不合格的组件仍可发布 offline。人工 ELB 配置等步骤不自动执行。

声明 configuration 时，软件组件必须提供 configuration: [{path: 相对文件名, content: 配置内容}]。仅支持 ${cluster}、${instance}、${params.参数键}、${host.name}、${host.ip}、${host.data_root} 文本占位；不执行 Jinja、shell、查找插件或脚本。每个实例/机器独立输出，未知占位符会阻止生成。复杂配置仍使用经过验证的部署流程。仅出配置不会安装软件，也不会把文件生成成功记录成部署或验收通过。

新建交付选择材料类型；生成后在现场执行页选执行节点和独立步骤，核对集群名称并授权。发布组件不是执行授权。执行期间固定快照及运行环境标识，同一集群或机器不允许并发批次；失败不自动重试，状态未知保留占用。暂停在步骤边界生效。恢复网络仅补传已有事件，不能重跑已有尝试。

自动执行器使用已准备运行包的 bin/ansible-playbook，不能使用不存在的 bin/ansible。节点位于交付控制机器，当前不支持任意独立管理机；全离线环境继续按手册执行后导入日志。节点认证令牌和现场密码不进入 AI。

每次尝试保存步骤、机器、开始/结束时间、退出码、机器汇总、固定快照和日志。报告区分执行节点验证、上传日志与人工确认；未执行、跳过、失败、状态未知都不能记成通过。页面默认显示结果摘要，可切换详细证据并按相同范围导出 Word。旧快照的记录保留供追溯，不重新计算为新修订的成功结果。
