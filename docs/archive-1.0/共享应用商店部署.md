# Middleware Hub 共享平台部署与使用

多人通过浏览器选择应用、填写部署规格（表单或 YAML）、上传证书、预览并生成离线交付：每台机器一个上传包、一套 Ansible 工程和按本次配置填好的现场手册。**平台只生成材料，不连接任何目标机器**；现场仍通过堡垒机人工上传并按手册执行。生成成功不代表部署成功。

应用不是代码，而是数据：每个中间件是一份组件清单（`component.yaml`，可带 Ansible 角色与配置模板），平台里没有任何应用特例。设计见《组件清单设计.md》，界面约定见《界面设计规范.md》。

## 当前范围

- **内置组件**：etcd；PostgreSQL 17（无从库时是单节点，有从库时是 Patroni 单主高可用并自动加入协调服务 etcd；可选 TLS、TDE、pgBackRest 与 WAL 归档、数据库扩展）；HAProxy、Nginx（stream）、keepalived（虚拟 IP）；外部负载均衡（只生成云 ELB 配置清单）。
- **放置自由**：机器列表由用户填写，每个角色放到哪几台机器由用户决定；入口可以是新的两台机器加 keepalived、与数据库同机，或客户自己的 ELB。平台只校验（角色数量、端口冲突、端点与负载均衡能力是否匹配），不限制。
- **依赖自动补全**：例如 PG 有从库就自动加 etcd，HAProxy 选 keepalived 就自动加 VIP；在界面里可以“自行指定”改成独立机器、不同端口或版本。
- **版本**：每个组件可有多个版本，版本之间的制品、参数、依赖、角色可以不同；生成时记录 `deployment.lock.json`，并把补全后的规格（含版本与控制节点）原样保存，可重新生成同样的交付。
- **录入新应用**：管理员在“组件”页导入组件包（.tar.gz/.zip，含 `component.yaml`，可带 `roles/`、`templates/`、`files/`）或粘贴只含清单的纯声明式组件，校验通过后立即可用，无需重启或改代码。
- **状态如实标注**：组件版本分 `draft`、`verifying`、`published`；未发布的版本在界面和手册里都会提示“尚未在空环境验证”。

### 边界

- **没有在真实 Ubuntu 机器上执行过任何由本平台生成的部署。** 生成物经过 Ansible 语法检查（ansible-core 2.14 与 2.20.10）和全部配置模板的真实渲染，但行为须在空集群上验证；所有内置组件版本因此不是 `published`。
- **软件包由平台的软件库提供**：清单里只写软件包名和确切版本，平台按目标系统自己知道去哪下载（Ubuntu 官方源、Percona、Rocky 等，管理员可以改成内网镜像）。能联网就在“软件库”页点“更新索引”（联网一次），之后搜软件包、查所有版本、预览依赖都是即时的，确认后一键下载到本地缓存；不能联网就随平台发布时带上准备好的软件库，需要新软件包时在联网机器上获取后导出，回平台导入。生成交付时不需要 Docker 也不需要网络。
- **红帽系的控制节点**：红帽系 9 自带 Python 3.9，而 Ansible 2.20 要求控制节点用 3.12。所以每份红帽系的交付都会多带一个 `python3.12`（及依赖，约 17 MB）进 `packages-el9-amd64.tar.gz`，控制节点上的 `bootstrap/bootstrap-ansible.sh` 先用这个离线仓库装好 `python3.12`（只启用这一个仓库，不动系统的其他软件源），再装私有的 Ansible。被管节点仍用系统自带的 Python 3.9。运行环境包是 `ansible-runtime-el9-amd64.tar.gz`，放在材料目录里自动识别；用 `middleware-automation/packaging/build-el9-runtime.py` 从 Ubuntu 的运行环境包生成（wheel 是同一批，只换引导脚本）。
- **操作系统**：部署规格选一个操作系统，所有机器必须是它。目前登记 Ubuntu 24.04 和 RedHat 系 9（RHEL / Rocky / Alma）。RedHat 系的软件包目前备了 HAProxy、Nginx、keepalived 和控制节点要用的 python3.12，并有自己的 Ansible 运行环境，可以生成交付；但它的部署还没有在真实机器上执行过（含 SELinux 的影响）。
- Patroni 单主架构，不支持多主；两个 etcd 成员不能容忍一台失联（界面与手册会提示）。
- 没有成员变更、扩缩容、升级；没有 Redis、Kafka、MySQL 组件（模型为它们设计，尚未编写）。
- 账户分 admin/operator；交付者只能查看、下载和删除自己的交付，管理员也不能通过界面下载他人的私钥。单进程服务，生成并发默认 2、单用户排队/运行最多 3、全局最多 20；重启会使未完成任务标记失败。

## 1. 准备平台服务器

Linux amd64 + systemd，建议 Ubuntu 24.04。需要一个独立的平台 PostgreSQL 数据库及账户（本库建表权限即可，不需要超级用户），元数据和交付目录都要纳入备份。准备平台访问域名与 HTTPS 证书（这是网站自己的证书，与上传给待部署集群的证书是两回事）。

## 2. 安装

把 `middleware-store-vX.Y.Z-linux-amd64.tar.gz` 及同名 `.sha256` 上传到平台服务器：

```bash
sha256sum -c middleware-store-*.tar.gz.sha256
tar -xzf middleware-store-*.tar.gz
cd middleware-store
sudo bash install.sh
```

安装器校验完整性，创建服务账户，把程序放到 `/opt/middleware-store`，把离线材料放到 `/var/lib/middleware-store/artifacts/`，不自动启动；已有平台目录时拒绝覆盖。包里含程序（前端与内置组件都嵌在里面）、Ansible 离线运行环境、**准备好的软件库**、systemd 与配置示例，不含任何客户私钥或密码。

### 数据目录里的东西

|位置（默认）|内容|
|---|---|
|`<data_dir>/library/`|软件库：每个操作系统一个目录，含 `pool/`（软件包文件）、`meta/`（索引元数据）、`closures/`（每个“软件包@版本”的依赖闭包）|
|`<data_dir>/sources.yaml`|管理员自定义的软件源（覆盖内置源）|
|`<data_dir>/components/`|导入的自定义组件|
|`<artifacts_dir>/ansible-runtime.tar.gz` + `.sha256`|每个控制节点解包后离线安装的 Ansible 运行环境（Ubuntu 24.04 用）|

清单里的 `artifacts` 现在只用于普通文件；软件包一律走软件库。缺少软件包时，需要它的组件显示“软件库缺 N 个包”，生成时拒绝并写明缺哪些。

### 准备软件库（发布前做一次，需要 Docker 和网络）

在一台有 Docker 和外网的机器上，用同一个程序：

```bash
# 把所有内置组件需要的软件包一次备齐（每个系统各跑一次）
middleware-store library fetch-all --library ./package-library --platform ubuntu-24.04-amd64
middleware-store library fetch-all --library ./package-library --platform el9-amd64
# 查看库里有什么 / 看软件源现在能提供哪些版本
middleware-store library list --library ./package-library
middleware-store library versions --library ./package-library --platform ubuntu-24.04-amd64 --package haproxy
# 只补某几个，并证明它们能在断网的干净容器里单独装上
middleware-store library fetch  --library ./package-library --platform ubuntu-24.04-amd64 --pkg haproxy=2.8.30-0ubuntu0.24.04.1
middleware-store library verify --library ./package-library --platform ubuntu-24.04-amd64 --pkg haproxy=2.8.30-0ubuntu0.24.04.1
```

下载在目标系统的容器里进行（`ubuntu:24.04`、`rockylinux:9`），依赖由真正的 `apt`/`dnf` 解析，软件源签名全程验证（rpm 另外逐个 `rpmkeys --checksig`）；网络中途失败会重试，已完成的软件包先入库，重跑只补缺的。之后打发布包：`python3 packaging/build-store.py --library ./package-library`。

### 平台已部署、之后要补软件包

- **平台服务器能联网（不需要 Docker）**：管理员在“软件库”页选操作系统 → “更新索引”（首次一次，之后想看到新版本再更新）→ “添加软件版本”：搜软件包、选版本，立刻看到它要下载的全部依赖和大小，加入清单后“下载到本地”；进度实时显示。Ubuntu 和 RedHat 系 9 都这样用。
- **外网建库、内网使用**：在联网的平台更新索引、下载软件包后，点“导出索引”和“导出全部”得到两个 `.tar.gz`；带到内网平台，在“软件库”页分别点“导入索引”和“导入”。导入会重新验证签名与哈希，来源不对或被改动的包被拒绝，比现有更旧的索引也被拒绝。之后内网平台不联网即可搜软件包、查版本、预览依赖，并生成部署手册。要看到新版本：外网重新更新并导出索引，再导入内网。
- **平台服务器离线（常态）**：在联网机器上 `library fetch` 获取，`library export --pkg 名称=版本 --out 文件.tar.gz` 导出，回到平台“软件库”页点“导入”。每个文件都核对哈希，任一项不符整包拒绝。
- **内网镜像**：“软件库 → 软件源”里按 `id` 覆盖内置源，把地址改成镜像（例如 `id: ubuntu-noble` 的 `url`）；也可以新增源或停用某个源。保存后对以后的获取生效。

## 3. 配置

`/etc/middleware-store/service.env` 设置 `MIDDLEWARE_STORE_DATABASE_URL`（密码特殊字符按 URL 编码；示例用 `sslmode=verify-full`，根 CA 放 `/etc/middleware-store/db-ca.crt`）。连接信息只通过环境变量注入，不下发到浏览器或交付包。

`/etc/middleware-store/config.json`：

```json
{
  "listen": "127.0.0.1:8090",
  "public_url": "https://middleware-store.example.internal",
  "data_dir": "/var/lib/middleware-store",
  "components_dir": "/var/lib/middleware-store/components",
  "artifacts_dir": "/var/lib/middleware-store/artifacts",
  "runtime_archive": "/var/lib/middleware-store/artifacts/ansible-runtime.tar.gz",
  "library_dir": "/var/lib/middleware-store/library",
  "sources_file": "/var/lib/middleware-store/sources.yaml",
  "database_url_env": "MIDDLEWARE_STORE_DATABASE_URL",
  "max_parallel": 2
}
```

`components_dir`、`artifacts_dir`、`runtime_archive`、`library_dir`、`sources_file` 都有默认值（`data_dir` 下），可省略；`ansible_bin`（可选）是本机 ansible-core 的 `bin` 目录，组件工作台用它做 Ansible 语法检查和模板渲染预览（不配置时依次找环境变量 `MW_ANSIBLE_BIN`、`<data_dir>/ansible/bin`、PATH；都没有就只是少了这两项检查，其余照常）；`docker` 可指定容器客户端（默认 `docker`），不装也行，只是不能在线获取软件包；`runtimes` 可为其他操作系统登记 Ansible 运行环境（键是系统 id）。`public_url` 不带末尾斜线，来源与 Host 按它校验。可由同机 Nginx 终止 HTTPS（参考 `deploy/nginx.example.conf`，须保留原 Host、允许 12MiB 上传、给下载足够时间），也可由程序直接提供 HTTPS（`tls_cert`/`tls_key`）。非回环监听不接受明文 HTTP；共享服务必须配置平台 PostgreSQL。

## 4. 创建首个管理员并启动

```bash
sudo -i
set -a; . /etc/middleware-store/service.env; set +a
read -rsp '平台管理员初始密码: ' STORE_BOOTSTRAP_PASSWORD; printf '\n'
printf '%s' "$STORE_BOOTSTRAP_PASSWORD" | /opt/middleware-store/bin/middleware-store store user-add --config /etc/middleware-store/config.json --username admin --role admin --password-stdin
unset STORE_BOOTSTRAP_PASSWORD
systemctl enable --now middleware-store
journalctl -u middleware-store -n 100 --no-pager
```

首次连接自动创建 `middleware_store_*` 表。其他账户由管理员在“账户”页添加，密码至少 12 字符。

## 5. 使用

1. **应用**页选一个应用，点常用方案或“自定义”；**新建交付**向导共五步：集群与规格 → 机器 → 组件与放置 → 参数 → 入口与证书。
2. 每次修改，右侧预览都会重新解析：自动加入了哪些组件、哪里有问题、会生成哪些文件、分哪些阶段部署。有阻断问题不能生成；提示（如版本未验证）不阻断。
3. 左下角“查看 / 导入 / 导出 YAML”：表单与 YAML 是同一份数据，可复制、下载、编辑后导入；也可以用命令行直接生成：

```bash
middleware-store render --spec 规格.yml --out 交付目录 --library 软件库目录 --runtime ansible-runtime.tar.gz [--cert-dir 证书目录]
```

4. 生成成功后在**交付**页下载整包 ZIP 或单个文件；“现场执行”按篇章列出每一步（执行机器、影响、通过标准、命令），勾选进度只保存在当前浏览器。
5. 现场：先上传并解包、完成免密配置，再在控制节点依次执行部署各阶段、功能测试、入口测试、清理；每一步 Ansible 末尾须 `failed=0`、`unreachable=0`。密码由控制节点自动生成保存，不进入手册和日志。
6. 部署后在交付页把结果标为“完成”或“失败”，这是用户回报，与平台生成状态分开。
7. 删除交付只删除平台上的文件与记录，不会登录或清理目标机器。

下载内容可能含客户私钥，请按内部规范管理；平台管理员能管理服务器存储和数据库，界面隔离不等于对服务器管理员加密。

## 6. 管理组件

“组件”页列出全部组件及来源（内置 / 自定义 / 覆盖内置 / 未发布的草稿）。管理员可以：

- **在工作台里编辑**：内置组件点“新建版本…”（覆盖内置，可随时“恢复内置”）或“复制为自定义组件”；自定义组件点“编辑”；“新建”用单进程服务 / 主从 / 对等集群模板起一个新组件。草稿自动保存，发布前先“检查”和“试生成”，发布时写修订说明，之后可以对照任意修订、回到它。操作说明与三篇教程在“怎么编写和修改组件”（`#/components/guide`），设计见《组件清单设计》第 16 节；
- **导出**任一组件为组件包，作为新组件的样板；
- **导入**组件包或粘贴清单，先校验后安装，校验失败逐条给出位置与原因，已装的不受影响；
- **删除**自定义组件（内置不可删；删除“覆盖内置”的会恢复内置版本）。已生成的交付不受影响。

组件的草稿与修订历史在 `components_dir/.work/` 与 `components_dir/.history/` 下（以点开头，载入器忽略）；备份 `components_dir` 时一并带走。

组件包规则：根目录（或唯一的一层目录）含 `component.yaml`，其余只允许 `roles/`、`templates/`、`files/`；不接受链接、路径穿越、超过 8MiB 或 400 个文件。声明式步骤只能使用 `ansible.builtin` 里的安全模块，禁止 `shell` 和 `ignore_errors`；`template`/`copy` 的 `src` 必须随包提供；复杂逻辑写成 `roles/`。清单里的 `when`、`default`、`rules` 使用表达式（`params.x`、`roles.primary`、`count(...)` 等）。

## 7. 交付的现场执行记录

平台不连目标机器，现场的执行情况由执行人在交付页的手册里记录：每一步可以勾选完成，也可以点“记录结果或粘贴输出”标为完成、失败或跳过，写一句备注并贴上终端输出（单步最多 64 KiB，整个交付最多 3 MiB）。记录保存在平台（`jobs/<id>/progress.json`，与交付材料放在一起，随交付删除而删除），交付的所有者在任何浏览器里看到的都一样；手册里的“执行记录”页签按时间列出谁在什么时候做了什么，失败的一步会写明原因。交付列表里显示“现场 7/17 步，1 步失败”。早先只存在浏览器里的勾选在第一次打开时自动迁到服务器。接口：`GET/PUT/DELETE /api/jobs/{id}/progress`（仅交付所有者，需要 CSRF）。

## 8. 安全：漏洞库与交付的已知漏洞

“安全”页把**厂商公布的安全通告**和每份交付**实际安装的软件包**比对，回答“这份交付有没有已知漏洞”。

- **数据来源**：Ubuntu 24.04 用 Canonical 的 USN 通告（OVAL，`security-metadata.canonical.com`）；RedHat 系 9 用 Red Hat 的补丁通告（OVAL，`security.access.redhat.com`，Rocky/Alma 的软件包与它同源，按 rpm 版本比较）。两份都是厂商官方的 HTTPS 地址。Red Hat 同时公布文件哈希，下载后会核对；Canonical 没有公布哈希或签名，只能保证文件与下载时一致。**不是签名校验**，界面上如实标注。
- **更新**：管理员在“安全”页右上角“漏洞库”里点“联网更新”（平台所在网络要能访问上面两个地址）。平台在内网时：在能上网的机器上运行同一个平台，更新后点“导出”得到 `vuln-<系统>-<日期>.tar.gz`，用你们传文件的办法带进内网，在内网平台点“导入”。导入时重新计算哈希、重新解析、核对来源地址、拒绝比现有更旧的数据，包里的说明只拿来对照，不被信任。
- **比对**：以交付的 `deployment.lock.json` 里的软件包为起点，取软件库里它们的完整依赖（版本精确），逐个与通告里“从哪个版本起修复”比较（deb 用 dpkg 规则，rpm 用 epoch:version-release；rpm 模块流的通告只用于同一模块流）。
- **判断**：对每条发现可以记录“不受影响 / 已缓解 / 接受风险”，必须写原因，记录人和时间（保存在交付目录的 `security.json`，操作写入审计）。已判断的不再计入待处理。
- **局限（界面上也写明）**：只列厂商已公布**并有修复版本**的漏洞；不检查内核通告；没有提示不等于没有漏洞；不判断漏洞在具体配置下能否触发；数据有厂商发布的延迟。
- 接口：`GET /api/security`、`POST /api/security/update`、`GET /api/security/export`、`POST /api/security/import`、`GET /api/security/deliveries`、`GET /api/jobs/{id}/security`、`PUT /api/jobs/{id}/security/marks`。

## 8.0 定期扫描与扫描记录

安全页左侧是三个入口：总览、扫描记录、漏洞数据。平台在漏洞数据或软件库变化后自动重新扫描（每分钟检查一次是否有变化），并在每天设定的时间（默认 02:00，可关闭）复查一遍；每次扫描都记录下来：扫描了多少软件包、对照多少通告、待处理多少、与上一次相比新发现和消除了哪些。任何人可以「立即扫描」。能上网的平台可以设置每天或每周自动更新漏洞库（默认关闭，内网平台用导出、导入）。记录在 `<data_dir>/security/`（scans.json 保留最近 120 次，settings.json）。

## 8.0.1 漏洞库浏览、Ansible 运行环境、通知

- 安全 → 漏洞库：按系统搜索全部厂商通告（通告编号、CVE、软件包、标题），可筛选严重程度、只看影响自己软件包的。
- Ansible 也在扫描范围：每个系统多两行，「Ansible 控制节点」（控制节点需要的系统包，用厂商数据）和「Ansible 运行环境」（运行环境里的 Python 包，用 OSV 的 PyPI 通告）。OSV 数据在「漏洞数据」里联网更新（只查询运行环境实际带的包），可导出、导入，供内网平台使用。交付本身的安全报告目前只含系统软件包。
- 自动更新间隔可选：关闭、每小时、每 2/6/12 小时、每天、每周。
- 平台设置（管理员，头像菜单 → 平台设置）→ 通知渠道：企业微信、钉钉、飞书群机器人和通用 Webhook，可测试，有发送记录。安全 → 漏洞数据 → 通知里选择用哪些渠道、多严重的新漏洞才通知、自动更新失败是否通知。

## 8.0.2 Ansible 运行环境由软件库拼装

交付里带给控制节点的离线 Ansible 不再是事先打好的压缩包。软件库 → Ansible 运行环境：

- 平台按版本从 PyPI 下载 wheel（pip 自动解析依赖，按控制节点的 Python 3.12 / x86_64 选包），存进软件库；一个「运行环境」就是一份确切的 wheel 清单。
- 每个系统选一个默认运行环境；生成交付或方案时当场拼装：wheel + 内置的安装脚本（`runtime_assets/`）+ 带哈希的 requirements.lock。
- 有漏洞时点「生成修复版本」：保留原有包，只把有漏洞的升到修复版本，重新解析依赖，并设为默认。之后的交付和方案都带新的；已交付的集群可在安全页生成补丁方案，只更新控制节点上的运行环境（安装脚本发现清单变了会重装，旧的保留为 runtime.prev）。
- 可导出、导入，供内网平台使用；也可以只用软件库里已有的包（不联网）组成运行环境。
- 首次启动时，原来配置的运行环境压缩包会自动导入为第一个运行环境并设为默认，已有功能不受影响。
- 验证：在断网的 Rocky 9 容器里，用交付自带的离线仓库装上 Python 3.12，装好原运行环境（pip 25.3），清单不变时复用，换成补丁方案的运行环境后重装为 pip 26.2，ansible-playbook 2.20.10 正常运行。

## 8.1 升级、补丁、扩容、缩容方案

交付页的「生成方案」选一种（升级、补丁、扩容、缩容），用已有交付的配置打开向导（标识自动取 `-c1`、`-c2`……）：改版本、加减机器、挪角色，右侧实时显示本次变更和各阶段步骤；与来源没有差异、组件没有声明对应的变更步骤、来源是单节点等情况会直接在右侧指出。生成的交付写明来源，来源不会被改；同一来源的多份变更互斥，交付页会提示。变更交付没有建集群的阶段，第一阶段只读核对现状。安全页的「生成补丁方案」把可修复的软件包固定为修复版本。详见《扩缩容与升级方案.md》7.1、7.2。

## 漏洞数据：已修复的和还没修复的（1.0.74-dev）

平台有两类漏洞数据，「联网更新」会一起下载，「导出 / 导入」也一起带走：

- **厂商安全通告**（Ubuntu USN、Red Hat RHSA）：哪个软件包从哪个版本起修复了哪些漏洞。只在厂商发布了修复之后才有。
- **CVE 目录**（Ubuntu CVE OVAL、Red Hat「含未修复」OVAL）：厂商已经公布、还没有修复的漏洞，以及厂商对每个软件包的结论。每个系统约 1 万多条，原始文件各约 10 MB，保存在软件库 `vuln/<系统>/cves.raw`，旁边有解析后的压缩缓存。

**什么算漏洞，什么不算**

- 只有「厂商**已确认**受影响、还没有修复」的才算待处理的漏洞：已确认受影响暂无修复、推迟修复、不予修复、超出支持范围（Red Hat 的 Affected / Fix deferred / Will not fix / Out of support scope）。
- 厂商还**没有确认**的（Ubuntu 的「可能受影响，可能需要修复」、Red Hat 的 Under investigation）不算：不进交付的待处理数量、不进扫描和通知、不在「影响我的交付」列表里出现。它们只在「漏洞 → 全部已公布」里可以搜索、查看，页面上明确标注「待厂商确认」。Ubuntu 的数据本身不区分「已确认」和「待评估」，所以 Ubuntu 系统上目前没有「已确认暂无修复」的项，这是数据源决定的，不是漏检。
- 只写入**属于我们软件**的漏洞：按每份交付实际安装的软件包名对照；软件包不在交付里的 CVE 只在「全部已公布」里可查，不进任何扫描记录。
- Ansible 运行环境（Python 包）的漏洞也在同一个页面里，厂商没有给出修复版本的算「已确认暂无修复」。

**豁免**：客户环境用不到的漏洞（没启用相关功能、端口不开放……）可以豁免。在「漏洞」页勾选后选「记录处理结果 → 已豁免」，写明理由（必填）、可选复审日期；默认对所有交付生效，包括以后新生成的交付（成为「豁免规则」，在页面右上角「豁免规则」里查看和撤销），也可以只对这一份交付豁免。豁免和理由、操作人一起记录并进审计。复审日期到了，它重新算待处理。

**页面**：安全 → 「漏洞」列出影响你交付的 CVE（含已有修复的和暂无修复的），可批量记录处理结果或让 AI 一起评估；可搜索任何已公布的 CVE；每个 CVE 一页：厂商怎么说、影响哪些交付、临时缓解办法、记录处理结果、让 AI 给出处置方案。交付页有「厂商已确认、暂无修复的漏洞」一节。处理结果沿用原来的记录方式（键为 `CVE编号|软件包`）。

局限：只覆盖目前有数据源的系统（Ubuntu 24.04、RHEL 9 系）；厂商还没有收录的新 CVE（刚公布的几小时内）看不到；Red Hat 的模块流软件包按包名匹配。
