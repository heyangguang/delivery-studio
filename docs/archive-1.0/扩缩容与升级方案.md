# 变更类交付方案：扩缩容、成员变更、升级与漏洞修复（草案，供讨论）

这一版重写了上一版。上一版把“变更”当成在原交付上继续做，那是错的：平台是离线的，不连集群，只负责**产出交付**。所以下面所有事情的形式都是——**基于某个已有交付，生成一份新的交付**。原交付永远不改，它是历史记录；新交付写明“从哪个交付派生”。

状态：只是方案，没有写代码。第 7 节是需要和你讨论、定下来的问题。

## 1. 统一的做法：派生交付

```
原交付 A（集群当初怎么部署的：规格、软件包版本锁）
   │  用户在这里描述“想变成什么样”（加两个节点 / 升到新版本 / 修这几个漏洞）
   ▼
新交付 B  = 目标规格 + 与 A 的差异 + 变更步骤 + 手册 + 软件包（只带需要的）
```

- B 是一份和现在完全同类的交付：一包材料、一本手册、一份现场执行记录。生成、下载、现场执行、记录，全部沿用现有链路，平台不需要新增任何“连接集群”的能力。
- B 记录 `derived_from = A`（只是说明来历，不会去改 A）。交付页里能顺着看到一条链：A → B → C。
- 平台不知道集群现在的真实状态，只知道 A 部署时的样子。所以 B 的第一步固定是**只读的现状核对**（由组件声明怎么核对），和 A 对不上就停，让现场先人工对齐。这是唯一的安全网，我们不假装平台知道现状。
- 同一个 A 可以派生出多个 B（比如先出一个“加节点”方案，再出一个“升级”方案），互不影响；真正执行哪个、先后顺序，由现场决定，执行记录里留证据。

## 2. 三类派生

| 类型 | 用户做什么 | 平台产出什么 | 需要组件懂什么 |
|---|---|---|---|
| 扩容 / 缩容 / 成员变更 | 在 A 的规格上加减机器、换一台机器 | 目标规格与 A 的差异、新增机器的软件包、逐台执行的变更步骤、每步后的检查 | 组件要写明“这个角色怎么加入、怎么摘出”（如 etcd 的 member add/remove、Patroni 加从库） |
| 升级 | 选目标版本 | 新版本软件包（只带差量）、升级顺序与步骤、升级前的快照/备份检查 | 组件要写明“从哪些版本能升到哪些版本、怎么滚动” |
| 漏洞修复（CVE） | 看到受影响的交付，点“生成修复交付” | 把受影响的软件包升到修复版本的升级交付 | 组件要声明“这个包的小版本升级是安全的”；有声明就能直接生成，没有就提示需要人工评估 |

前两类依赖组件的专业知识（工作台里写 `changes`，见第 5 节）；**漏洞这一类大部分是平台本身的事**，不要求组件作者额外写什么，所以我建议它优先。

## 3. 漏洞（CVE）相关能力

要回答的是离线环境里最常被问的话：“我们部署出去的这些，现在有没有已知漏洞？有就怎么办？”

1. **漏洞库**：和软件库的软件源索引完全一样的思路——联网平台下载厂商公开的安全通告数据，导出，带到内网平台导入。数据来源按系统分：Ubuntu 用官方安全通告（OVAL/USN），Rocky/RHEL 用官方勘误数据。导入时记录来源、日期、哈希，拒绝比现有更旧的（防回退），和索引的导入规则一致。
2. **比对**：每份交付的 `deployment.lock.json` 里有精确到版本的软件包清单（连同依赖），拿它去比漏洞库，得出每份交付的“已知漏洞”：CVE 编号、严重程度、哪个软件包、现在的版本、修复版本。
3. **展示**：
   - 交付详情里一块“安全”：几个高危、几个中危，点开看明细；
   - 一个汇总页：哪些交付受影响、按严重程度排序、哪些已有修复版本在软件库里（可以立刻出修复交付）、哪些修复版本还没下载（提示去软件库下载）。
4. **不能只看数字**：允许标注“不受影响 / 已缓解 / 接受风险”并写原因（谁、什么时候），后续不再重复提醒；这是正式安全流程需要的，不是装饰。
5. **生成修复交付**：选中一份交付，选“把受影响的包升级到修复版本”，平台生成一份升级类派生交付（第 2 节）。如果某个修复涉及组件没声明可安全升级的包，明确列为“需要人工评估”，不替用户做决定。
6. **局限，要先说清楚**：漏洞库只能告诉“这个包的这个版本有已公布的漏洞”，不能证明“没提示就是安全”；厂商数据的更新有延迟；有些漏洞要求配置条件才触发，平台判断不了。界面要如实写，不夸大。

## 4. 软件包与离线的配合

- 升级 / 修复交付只带**新增和变化的包**（以及它们的依赖差量），不重复打包没变的，包会小很多。
- 需要的新版本不在软件库时，不能生成，提示去软件库下载（沿用现有检查）。
- 联网平台和内网平台的分工不变：漏洞库、软件源索引、软件包都由联网平台准备并导出，内网平台导入。

## 5. 组件怎么声明“怎么变”

沿用现有的组件清单思路，在 `component.yaml` 里增加可选的 `changes:`，步骤的写法和 `lifecycle` 相同（有影响等级、预期、角色任务文件或内联任务）：

```yaml
changes:
  precheck:  [...]          # 只读现状核对（和原交付对得上吗）
  scale:                    # 按角色：怎么加、怎么减
    member: {add: [...], remove: [...]}
  upgrade:                  # 从哪些版本升到哪些版本，怎么滚动
    - {from: ["3.5.*"], to: "3.5.*", strategy: rolling, steps: [...]}
```

没声明的组件，对应按钮不出现并说明“这个组件还没有扩缩容/升级步骤”。工作台里相应加表单和试生成（“试生成”里选择“从某个交付派生”预览变更包）。

## 7. 已讨论确定的结论

1. 方向确定：所有变更都是新交付，原交付只读。**未来平台会提供连接集群的能力**，现在的设计不要堵死它——所以派生交付的“现状核对”“执行记录”都按“将来可以由平台自己执行并回填”来设计，现阶段仍由现场人员执行。
2. **先做漏洞（P1）。**
3. 漏洞库的更新方式（联网平台下载、导出文件、人工带进内网平台导入）：待向你解释并确认，见下面“数据怎么进内网”。
4. **不做**“手工录入现状”：用户想升级就按现有交付里的信息自己填写目标，平台出升级方案。
5. 一份交付可以派生多份备选变更，手册和交付页提示它们互斥，现场只执行一份。
6. 关联变更放在**同一份**派生交付里，按依赖顺序排好，用户可以勾掉不想现在做的。

### 数据怎么进内网（待确认）

漏洞信息是厂商在互联网上公布的，内网平台自己拿不到。有两种情况：

- **平台所在网络能访问互联网**：界面里点“更新漏洞库”，平台直接下载，和现在软件库的“更新索引”一样。
- **平台在内网，不能上网**：另找一台能上网的机器，装同一个平台（或同一个程序），在那里点“更新漏洞库”，再点“导出漏洞库”得到一个文件；把这个文件用你们平时往内网传文件的办法（堡垒机、U 盘、审批后的文件传输）带到内网平台，点“导入漏洞库”。导入时平台会重新核对文件没有被改过、来源是官方、没有比现有的更旧。这与现在“导出索引 / 导入索引”的流程完全一样，你们已经在用的那套。

## 7.1 P2 的实际做法（已实现）

- 交付页“生成变更交付”：用原交付的配置打开新建向导（标识自动取 `原标识-c1`、`-c2`…），生成的新交付记录 `derived_from`。只能基于**自己**的、**已生成成功**的交付；原交付不受任何影响。
- 交付页“变更来历”：基于哪份、派生出哪些、同一来源的其他变更（提示互斥），以及与来源的差异：机器、实例、版本、角色位置、参数、软件包（后者来自两份 `deployment.lock.json`）。
- 只读现状核对：变更交付手册的**第一阶段**有一步「核对集群现状与来源交付一致」，是 Ansible 步骤：逐台把已安装的软件包版本与来源交付当时安装的比对（版本带 epoch 一并比），任何一台不一致就失败并说明是哪个包。它是平台唯一的安全网，因为平台不连接集群。

## 7.2 P3 / P4 的实际做法（已实现）

**交付里写什么。** 部署规格里多一个由服务器填写的 `change`（来源交付、新增机器、移出机器、每个实例要做的操作 `upgrade / member-add / reconfigure / member-remove`）；用户不用写，也无法伪造：服务器用来源交付的规格和它的软件包清单与提交的新规格逐项比对得出。没有任何差异就拒绝（「没有差异，不需要变更交付」）。

**做哪些操作怎么判定。**
- 版本变了，或任何要安装的软件包与来源交付实际安装的不同 → `upgrade`。
- 某个角色多了机器 → `member-add`；少了 → `member-remove`。
- 自己没变、但它依赖（使用的协调服务、前面挂的负载均衡所在的）实例成员变了 → `reconfigure`；如果这个组件没有声明怎么调整，不静默跳过，而是在手册开头写一条「请自行确认」。
- 不做：新增或删除整个实例、换组件、改已有机器的 IP、单节点改高可用（这些直接拒绝并说明）。

**组件声明怎么做。** `component.yaml` 里的 `changes:`，按操作写步骤，写法同 `lifecycle`；机器选择多四种：`added:角色`、`existing:角色`、`removed:角色`、`first-existing:角色`；任务文件里用 `mw.change.existing / added / removed` 取机器。没有声明的操作，对应的变更会被拒绝。内置组件已声明：
- etcd：滚动升级、逐个加入（先登记再启动）、逐个移出（再停服务）。
- PostgreSQL：从库先升、主库先用 Patroni 切换再升；加从库（更新集群共享的访问规则、新机器装包、同步 TDE 密钥、加入复制、核对拓扑）；减从库（确认不是当前主库、停止、等它从集群消失、收回访问规则）；协调服务成员变化后重写 Patroni 配置并热加载。不支持更换主库所在机器。
- HAProxy、Nginx：滚动升级、新机器加入、按新后端重写配置并平滑重载、移出停服务。
- keepalived：滚动升级、节点加入或移出后重写所有节点配置并逐台重启。

**执行顺序固定：** 只读核对（机器、现状、密码文件）→ 准备新机器与软件源 → 升级 → 成员加入 → 调整相关配置 → 成员移出 → 只读复核 → 功能测试。变更交付不包含建集群的安装、配置、启动阶段。密码不重新生成：手册要求把来源交付项目的 `secrets/` 复制过来，并有只读步骤核对它们都在。

**CVE 修复。** 安全页上有「生成修复交付」：对软件包索引里已有修复版本、且是组件**直接安装**的软件包，把规格里的 `pins`（实例 → 软件包 → 版本）固定为修复版本，走上面的 `upgrade`。只是被带入的依赖不能这样修（需要重新解析依赖），会列出并说明。修复版本必须已在软件库下载。

**没有验证的东西。** 这些步骤只通过了 Ansible 语法检查、渲染检查和基线比对逻辑的本地测试；没有在真实的 etcd、Patroni 集群上跑过，上线前必须在空环境里按手册演练一遍。

## 7.3 按目的生成方案（2026-10-25 调整）

平台提供的是**方案**，不是「变更交付」：先由使用者说明要做什么，平台据此生成怎么做。顶部导航有独立的「方案」页：列出所有方案（可按类型筛选），「新建方案」先选要做什么、再选对哪一份交付；从安全页也能直接「生成补丁方案」。交付列表里不再混入方案。四类方案：

| 方案 | 做什么 | 允许的操作 |
|---|---|---|
| 升级方案 | 把组件升到新版本 | 升级，并跟随调整相关配置 |
| 补丁方案 | 把有漏洞的软件包升到修复版本（从安全页进入，已固定修复版本） | 同升级 |
| 扩容方案 | 增加机器或成员 | 成员加入，并跟随调整 |
| 缩容方案 | 减少机器或成员 | 成员移出，并跟随调整 |

方案类型记录在交付上（`intent`），手册写「这是一份升级方案」。修改与类型不符时（例如升级方案里又加了机器）直接拒绝并说明，请分成不同的方案生成；这样每份方案只做一件事，现场执行和回退都更清楚。其余机制（来源、互斥、只读核对、组件声明步骤）同 7.1、7.2。

安全页改版：默认进入「安全总览」，显示扫描范围（每个组件版本的软件包、含依赖的数量、各自的漏洞和历史通告对照数）、漏洞库状态、近 30 天新通告、近期披露且影响软件库里软件包的漏洞，以及每份交付的状况；判断依据和局限写在页面末尾。

## 7.4 方案向导只显示相关的部分（2026-10-25）

- 升级方案：只有「目标版本」一步，列出比当前新的版本，并显示「这次升级带来什么」（组件版本里写的 `released` 和 `notes`，以及要变化的软件包现在→升级后）。机器、角色、参数只读沿用。
- 补丁方案：只有「补丁内容」一步，列出每个软件包现在→修复到，以及修复的通告；不能自动修复的写明原因。
- 扩容方案：「新机器」「成员」两步；原有机器只读，只能在末尾添加。缩容方案：「成员」「机器」两步；原有机器地址不能改，只能删除。
- 组件版本可写 `released`（发布日期）和 `notes`（这个版本带来了什么，每条一句），工作台「版本」里可编辑。

## 8. 不做的事

- 不连任何集群、不自动执行、不自动回滚、不“监控现状”；
- 不承诺“没有提示 = 没有漏洞”；
- 不替用户决定风险是否接受，只记录他们的决定。
