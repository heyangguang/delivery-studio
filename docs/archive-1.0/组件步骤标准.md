# 组件与自动化步骤标准

适用于 PostgreSQL、Redis、Nginx 和未来组件。规则在组件目录加载、工作台校验和交付生成中执行。这是源文件归属与执行记录标准，不是任意脚本的安全沙箱。

## 步骤是最小变更单元

- ID 是长期身份；标题、显示顺序不能作为身份。
- 生命周期、升级扩缩容、验收、入口检查、清理都具有独立 Playbook。
- 阶段保留批量执行入口，步骤分别具有入口和记录。
- 新交付 plan.json 使用 step_format: 2；旧格式按旧记录键读取。一次历史阶段成功不能直接视为所有新子步骤成功。
- 修改 A 的私有实现，不得改变 B、C 的入口路径和内容。新增步骤不能重命名现有步骤。

## 私有文件与公共依赖

沿用 component.yaml，通过 run.role / run.tasks 指向固定入口，或使用受校验的内联任务。

源文件默认私有。检查器跟踪任务导入、角色导入及本地 copy/template/script 的源文件。同一文件被多个步骤引用时，必须拆开，或在组件顶层 shared_files 逐项声明，例如 roles/example/tasks/_wait_ready.yml 和 roles/example/files/runtime.py。

- 共享声明必须指向组件内真实存在的精确文件，禁止通配符。
- 未声明共享会导致目录加载、发布前目录校验和交付生成失败。
- 任务导入必须静态可解析，禁止动态选择任务文件和越界引用。
- 共享用于公共能力，不应用来把不同步骤的业务逻辑重新堆进大文件。
- 角色 defaults、vars、handlers 是角色级公共环境，修改可能影响多个使用者。
- 远端命令、动态运行时路径及脚本内部行为，不能仅凭源文件检查证明隔离。不要把检查通过理解为获得进程隔离或最小权限保证。

## 作者工作方式

1. 使用工作台模板。部署检查和验收使用不同任务文件。
2. 新步骤提供固定 ID、入口、目标节点、影响类型和成功预期。
3. 脚本、模板归属于步骤；公共工具明确登记共享。
4. 工作台校验全部通过。导入后的组件目录同样接受检查。
5. 预览交付，对所有独立入口执行语法检查，再检查更新的影响范围。

## 变更与历史

- 组件步骤在交付计划的 sources 中记录源文件路径、SHA256、是否共享。
- 影响分析比较实际执行文件和输入依赖，不用整个组件清单的总哈希判定所有步骤变化。
- 文件删除也按旧依赖图判断影响，不能漏报。
- 私有文件变动影响所属步骤；公共文件变动影响其使用者，并给出文件级原因。
- 标记变化不会自动触发初始化、恢复、故障切换或清理。
- 同步后的旧阶段记录保留原记录键，不冒充新子步骤成功结果。

## PostgreSQL 迁移实例

22 个动作分别有 tasks/test_<action>.yml、files/pgstep_<action>.py、templates/pgstep_<action>.json.j2。远端配置文件也按动作区分。

公共函数位于明确声明共享的 pgcommon.py，业务动作不互相导入。原 pgtest.py 多动作分发器已移除。公共库仍保留原配置初始化方式；如要实现字段级最小输入接口，需要继续收窄，不能宣称已经完成配置权限隔离。

## 必须验证的行为

- 修改真实 PostgreSQL、Redis、Nginx 步骤，无关步骤不标记更新。
- 插入步骤，后续入口不变。
- 未声明共享、通配符共享和越界引用被拒绝。
- 删除依赖文件，所属步骤标记更新。
- 旧格式保留旧键，新格式分别记录部署子步骤。
- 所有生成的阶段和步骤入口执行 Ansible 语法检查。
- Python 入口测试使用临时配置和替身，不接触数据库。

源文件和记录改造不代表真实集群部署已验证。上线前仍需覆盖新建集群、升级扩缩容、失败恢复以及旧交付同步后的现场执行。任意脚本的强制运行边界、统一字段级输入接口、集中结果协议及步骤前置条件执行门禁尚未由本次改动完整实现。

## 工作台与日志接入

工作台的“部署步骤”新增公共依赖文件选择器，组件作者与内置助手使用同一份 shared_files 声明。复制组件时，共享路径随角色目录重命名。

日志包含完整步骤路径。阶段执行额外生成子步骤日志；两个实例的同名步骤不会互相匹配。没有实际执行任务的子步骤记录为 SKIPPED，导入时保持未完成，不能自动当作验收成功。

## 步骤输入与可执行条件（本次续改）

步骤可声明 inputs，每个条目包含 type 和 value。支持 string、int、bool、list、map；任务通过 mw_step_inputs 读取。框架在任何业务任务之前校验输入类型，检查内容不进入日志，避免泄露凭据。

示例：

    inputs:
      timeout: {type: int, value: 7200}
    preconditions: ['mw_step_inputs.timeout > 0']
    postconditions: ['pg_test_result.rc == 0']

preconditions 与 postconditions 都是 Ansible 条件表达式列表，由生成器统一插入 pre_tasks / post_tasks。类型错误或前置条件失败时不执行业务实现；完成条件失败时整体执行失败。PostgreSQL 的 22 个验收/清理入口已采用独立超时输入及完成条件。

回调除保留兼容文本日志外，输出 STEP_RESULT JSON，schema 为 mwstep-result/v1，包含完整步骤路径、passed/failed/skipped 和结束时间。导入时检查 schema、步骤身份与文本结果的一致性；不一致不能当成功。

这是组件接口与运行结果契约，不是针对恶意管理员脚本的权限沙箱。旧组件可以继续使用 run.vars；把所有旧变量彻底迁移到最小输入集合，以及跨进程持久化的产物依赖门禁，仍需要后续迁移。

## 配置变化的精确判断

角色 defaults/vars 中的定义按实际使用关系递归展开。仅仅定义某个数据库参数，不再让每个使用这个角色的步骤都被视为读取该参数。无法静态判断的动态变量查询仍按可能受影响处理。

非入口 PostgreSQL 验收模板不再读取 ELB 配置；入口信息仅进入实际需要它的步骤。同步预览返回稳定步骤 key，不能只用可重复的标题识别步骤。
