# 组件编辑与方案联动设计

## 问题与目标

用户选单机后仍显示三台机器，原因是向导切换方案只更新角色放置，机器列表只增不减。组件概览混放产品介绍、三个方案和契约，参数与动作又按底层结构排列，无法以一个部署方案为中心理解。增加标准字段不能代替用户流程设计。

## 信息结构

保留一个 PostgreSQL 组件，不复制三份完整实现。基础、主从、高可用是三个独立方案；Patroni 是单独的管理组件，etcd 是其条件依赖。

组件编辑入口分为：
- 概览：名称、简介、适用场景；不混入方案契约表单。
- 部署方案：先选基础/主从/高可用，每次只显示一个方案。
- 公共定义：版本、参数定义、角色定义、复用动作。修改时应列出使用它的方案。
- 文件与源码：高级维护入口，不是正常填写方案的必经步骤。

一个方案内部按用户填写顺序组织：节点结构 → 需要的组件 → 配置项及默认值 → 访问入口 → 部署/验收/清理 → 支持的变更。系列契约由这些能力形成，必要的识别条件放在高级设置。不能让普通用户手写表达式来选择拓扑。

## 创建联动规则

1. 选择方案同时计算节点数量、角色、依赖、参数显隐、入口能力、验证条件。
2. 高可用切回单机，移除该方案不再使用的机器。其他组件仍使用的机器保留；界面区分数据库节点与入口/协调节点，不能把总机器数称作数据库节点数。
3. 已填写机器的映射尽量复用；若将丢弃用户填写的有效配置，展示明确差异并允许取消。临时空机器无需反复确认。
4. 单机不允许通过角色编辑器添加从库；主从不显示 Patroni 参数；普通主从不自动引入 etcd。
5. 方案是架构选择，内存、端口等调整不改变方案身份；已有部署的架构转换须单独迁移，不能当成普通改配置。

## 源码组织的目标

component.yaml 最终只作为入口，存放组件身份、schema 版本和各文件的显式引用。

建议按职责拆为：common/params.yaml、common/roles.yaml、common/endpoints.yaml、versions/*.yaml、schemes/single.yaml、schemes/replication.yaml、schemes/ha.yaml、actions/deploy/*.yaml、actions/tests/*.yaml、actions/cleanup/*.yaml。任务、模板、脚本继续使用已有的独立文件。

每个方案引用公共定义和自己的动作；禁止三份参数定义复制后独立漂移。引用须显式、局限于组件目录、禁止环和重复键。编辑公共文件时展示受影响方案；编辑私有动作仅影响实际使用者。

物理拆分必须同步完成加载器、文件安全检查、错误定位、工作台保存、AI 读取/编辑、复制组件、导入导出、版本快照及同步影响分析。不能只新增 include 或把文件藏进其他 YAML 就宣称完成。

## 1.0.217 实施范围

已实现：方案切换清理闲置机器和失效控制节点；保留其他实例仍使用的机器；移除已填 IP 的机器前确认；基础系列隐藏从节点入口。概览与部署方案分开，各系列独立选择和编辑，方案参数按公共定义使用类型控件，可恢复公共默认值。

多文件标准已实现：component.yaml 为入口，manifest/common 存公共定义，manifest/schemes 每方案一文件，manifest/actions 存阶段和独立测试、清理动作。内置组件全部迁移；线上 PG、Redis、etcd 保留原有配置语义。新建组件自动生成分片，旧单文件草稿继续可读，不覆盖用户已有草稿。

已接入加载、检查、保存、复制、AI 提案、导入导出、修订和版本状态。表单保存只回写所属文件，支持重排、改名、删除、新增和嵌套引用；源码入口提供分片跳转。共享实现仍按 shared_files 和步骤输入契约检查，文件拆分本身不冒充运行隔离。

验证记录见 多文件清单与方案联动验证记录.md。后续可进一步提供以方案为中心的完整依赖/动作总览及公共参数影响预览；当前公共角色、动作和依赖仍在对应专用页签编辑。
