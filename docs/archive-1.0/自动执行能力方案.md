# Middleware Hub 自动执行能力方案

日期：2026-11-11（Asia/Shanghai）。状态：首期基础能力在 1.0.242-dev 上线，1.0.243-dev 调整执行节点接入与交付执行界面；首期验收记录见同目录《自动执行验收-1.0.242.md》。下文保留整体方案；当前实现范围和验收边界见文末。

2026-11-11 场景复查修订：下一版设计以同目录《自动化场景与执行节点设计.md》为准。独立执行节点与集群内执行节点都属于必需使用场景，不再将前者放到后续。该文明确区分当前代码问题、下一版要求和业务验收；1.0.244 的落地范围以《自动执行接入验收-1.0.244.md》为准，完整设计不等于全部已实现。

## 目标与现有基础

在同一份交付中提供自动执行、人工执行和人工接管；部署、变更、测试、清理共用组件标准和步骤标识。PostgreSQL、Redis、Nginx 及后续组件走同一条流程。平台发布组件不等于更新已有集群。

现有代码已提供独立步骤 ID、输入、前后置条件、影响等级、超时、回退说明、组件及交付快照、步骤来源、同步差异分析、执行日志解析与 AI 提案。store_progress.go 当前主要记录人工填写的结果；ansible_runner.go 服务于组件校验，不是现场执行器。需要新增可靠执行服务，不能直接将现有生成任务改成远程部署任务。

## 推荐架构

平台负责选择范围、审核、编排与展示；客户网络中的执行节点负责下载交付、验证摘要、调用平台打包的 ansible-playbook、保存进度和回传日志。执行位置可以是集群内机器或独立管理机。已有获准的 SSH 通道时，目标机器可不安装 Agent；只有堡垒机会话而拿不到密码时，需要设计逐机 Agent 接入、授权公钥配置，或不依赖 SSH 的本机执行。具体路径、权限与验收见《自动化场景与执行节点设计.md》3.5.1；1.0.244 提供目标 Agent 配置 SSH 信任；无 SSH 的本机执行和现场中继仍未开放。

执行节点主动连接其可达的平台地址，不要求目标机器访问公网。凭据优先保留在客户执行节点，由平台引用授权名称；执行范围绑定环境、机器和集群。组件作者与 AI 不读取私钥。执行节点注册认证、主机身份核验、执行权限、作用范围检查必须由后端实施。

完全隔离的客户环境继续使用同一份离线执行包：本地执行后导出带步骤标识和版本信息的结果，导入平台。此模式不显示虚构的实时状态。

执行服务独立于网页和平台 Web worker 生命周期。关闭浏览器不停止任务；发布平台新版不终止现场进程。升级执行节点本身先停止领取新任务，已开始任务结束或到达安全暂停点后再升级。

## 用户流程与 UI

1. 新建交付仍从 AI 或表单填写，选择架构、机器、参数和入口。
2. 生成执行计划后显示集群、版本、机器、目录、预计操作和影响，选择“自动执行”或“手动执行”。
3. 自动执行先选执行节点并做连接与条件检查；确认本次执行范围后才进入队列。不会因查看页面、发布组件或生成卡片启动命令。
4. 当前现场执行页改为统一执行页，保留原阶段。每步显示等待执行、执行中、成功、失败、不适用、等待确认、状态待核实等状态；步骤详情显示当前机器、耗时、脱敏日志和验证结果。
5. “当前查看”是导航状态，“正在执行”来自执行节点事件；两者分开。人工勾选和自动验证的结果标明来源。
6. 自动流程可在步骤边界暂停，后续切换人工执行；人工处理后的自动继续必须重新检查前置条件。停止正在执行的步骤需要说明其停止能力，不能保证所有操作即时安全停止。
7. 新版本仅提示更新。已完成交付通过新的变更计划采用新版，不把原交付批量变回未完成。

现有页面增加：交付内的执行方式与控制栏；设置中的执行节点管理；自动归档的执行批次和日志。后续定时任务统一在自动化入口管理，具体操作继续落在所属集群和交付上。

## 三种需求处理必须由平台固化

| 类型 | 入口与记录 | 对现场的影响 | 长期配置 |
| --- | --- | --- | --- |
| 新需求 | 新增/修改操作提案，形成新的计划修订 | 审核后执行所选变更 | 成功验证后更新目标配置基线；支持下次重新生成 |
| 现场修复 | 关联失败步骤与证据的修复提案 | 修好当前问题，验证后从阻塞位置继续 | 如为临时措施，明确标记并安排固化 |
| 组件改进 | 独立组件建议/草稿，关联原故障和修复 | 组件发布不会自动操作已有集群 | 联合校验及发布后用于后续交付，已有集群自行选择变更 |

同一问题可以同时有现场修复和组件改进，分别审核，不要求现场等待组件发布。客户专属偏好不能自动成为所有组件的默认值。

除 skill 和系统提示，还应把 intent（需求变更/现场修复/组件改进）、关联步骤、目标范围、是否临时、验证方式持久化进提案。后端按类型校验；前端显示不同卡片；AI 工具使用同一模型。采纳、执行、验证成功、组件发布必须分别记录。

例如设置 node-2 为优先克隆源：提案包含目标参数 clonefrom_node=node-2、相应配置/热加载操作与验证；成功后保存应用基线。执行失败时保留待应用目标与实际状态的区别。不能只写临时命令，下一次生成又将其覆盖。

## 统一组件执行契约

扩展现有组件表单与分文件清单，不增加第二份专用于自动化的流程。

- 稳定步骤 ID、独立输入、文件与共享依赖，以及必要的步骤依赖。
- 执行方式：受支持的 Ansible 任务或人工步骤。AI 自由命令先形成可审核的有版本文件；未达到执行契约的步骤保持人工。
- 前置条件、运行目标、超时和结构化结果；成功既要求命令成功，也要求后置检查通过。
- 重试类型：可重复、重试前须检查、不可自动重试。缺少声明时采用保守默认，不因命令失败直接循环重跑。
- 中断服务与不可逆影响；确认点由组件声明与平台策略共同决定，组件不能降低平台的权限要求。
- 回退分为人工说明和经过验证的自动补偿步骤。不能把自然语言回退说明当成可自动执行的命令，也不承诺失败就自动回滚数据库。
- 组件发布的校验结果与“允许自动执行”资格分开。现有合格手动组件可继续发布；缺少执行约束时提示不具备自动执行条件。

机器参数、公共流程与组件参数继续通过现有契约表单定义，UI、后端和传参使用同一份定义。未来增加普通字段不需要修改每个创建页面。

## 步骤隔离、修订和真实执行范围

每次执行固定交付快照、组件修订、参数、执行节点和步骤摘要，执行中不读取最新组件。一次运行中的操作范围与确认内容不可悄悄扩大。

如果只改 A 的私有文件或输入，且 B/C 不依赖 A 的输出或共享依赖，B/C 的已有结果保留；如果修改公共文件、参数或 A 产物确实影响 B，就列出实际依赖链。不能承诺任何 A 变化永远不影响 B，也不能仅因同属一个组件就将所有步骤判为变更。

差异分析应区分：展示/记录格式变化、可证明行为相同的默认值补全、执行逻辑变化、目标配置变化、暂时无法证明。无法证明时要求复核，不能直接声称一定需要重跑。当前 data_root 缺省 /data 与显式 /data 的行为等价问题应在开放自动更新前补上回归证据；不能只按变量名忽略真实目录迁移。

同步或修复生成新修订，旧修订和其执行结果不可改写。新修订可引用经过规则验证仍然适用的成功结果；重试每次新增记录，不覆盖前一次。

## 执行可靠性

- 平台持久化执行请求、修订、步骤尝试、确认和事件；执行节点本地保存领取记录、进程状态与日志。日志不塞入当前受大小限制的 progress.json，现有执行记录作为兼容视图读取新数据。
- 请求有唯一标识，事件有执行批次、步骤、尝试号和递增序号；重复投递去重，断线后按游标补传。不能宣称远程写操作天然只执行一次。
- 平台与执行节点共同实施集群互斥；数据盘等公共资源增加主机/设备级互斥。同一资源不可由两个任务同时初始化或修改。平台外直接运行的命令无法完全受此锁约束，接管后须复核现场。
- 断网时执行节点可完成当前已授权步骤，默认停在下一步之前等待恢复。平台显示“连接中断，现场状态待核实”，不推断失败或成功。
- 心跳丢失或租约超时不能直接把同一写任务派给另一节点；先确认旧执行状态，必要时由人接管。平台重启后恢复调度前先核对执行节点记录。
- 密码/私钥不进入模型上下文和日志；日志脱敏，结果只对授权环境成员可见；下发文件、目录、运行器版本及摘要必须校验。

## 首期范围与后续

首期交付完整闭环：执行节点接入、授权范围、步骤执行、日志回传、暂停/失败/恢复、人工接管、AI 修复提案，以及相同组件用于手动和自动执行。先跑通 PostgreSQL 三种方案、Redis 常用方案、入口人工确认与自动测试。验证已有 Nginx/etcd 组件也通过同一契约接入，避免产品专属执行逻辑。

外部 ELB 没有已验证连接器时，明确显示人工完成步骤；确认后再执行入口验证，不能自动记为成功。涉及切主、故障注入、恢复数据等测试按维护窗口单独选择，不随普通健康检查自动执行。

第二阶段添加定时巡检、备份、证书到期检查等周期任务；支持执行窗口、并发限制、失败通知、错过调度处理，仍使用同一执行服务和记录。首期架构预留触发器，但先保证主动执行可靠。

第三阶段再扩展受控的发布/变更自动应用、云入口连接器和恢复演练。组件一发布就自动升级所有集群不作为默认行为。

## 验收标准

1. 同一规格的手动与自动计划使用相同步骤 ID、输入、来源版本和判断标准。
2. PG 单机、原生主从、Patroni 的组成与执行步骤对应；Redis/Nginx 不需要改执行器源码即可接入合格步骤。
3. 改 A 私有测试只影响 A；真实共享依赖变化准确列出影响；已有完成记录不丢失。
4. TLS/TDE 未启用只记为不适用，不记为通过；缺少入口的场景有人工或跳过原因。
5. 执行中关闭页面、平台更新、断网再恢复，任务与日志可追溯，不重复启动写操作。
6. 第二个并发修改任务被互斥规则阻挡；未知执行状态不可自动重派。
7. AI 现场修复只作用于当前计划，组件改进单独审核；新需求的配置在再次生成时保持一致。
8. 执行失败、超时、取消、人工接管、结果补传和权限拒绝都有明确 UI 与回归测试。
9. 使用隔离机器验证真实部署和故障恢复；仅读写平台测试数据不等同于自动部署已验收。


## 当前实现范围（截至 1.0.243）

已实现控制节点拉取、固定项目快照及运行器标识校验、集群/机器互斥、选择步骤授权、边界暂停、断线补传、重复事件去重、中断待核实、执行记录及报告摘要/证据导出。组件交付能力通过发布契约开放，配置交付独立生成配置包。AI 有读取当前交付执行批次与日志的工具；发起现场执行仍由有权限的用户确认。

当前节点必须安装在交付的控制机器；离线运行环境、SSH信任、软件包及证书先按手册准备。平台旧组件不自动改为 automatic，需作者在组件步骤中补齐超时、后置条件和判据，再发布新修订。平台不会改写已有组件草稿或交付。

独立执行节点、堡垒机逐机 Agent 接入和真实准备检查是本次自动化必须补齐的基础场景，尚未实现，不能与定时调度等后续扩展混为一谈。执行位置与连接方式分开建模；接入向导、状态区分、组件兼容与报告要求见《自动化场景与执行节点设计.md》第 8 节，实施与放行清单见第 9 节。Agent 本机执行必须通过跨机语义验收后才开放。定时调度、自动补偿、云入口连接器仍为后续能力。

本次验证使用隔离平台数据和 localhost Ansible 任务，不接触客户数据库。真实 PG/Redis 多机部署、网络分区和故障恢复仍需专用测试机器验收，不能把接口测试当成这些环境已通过。
