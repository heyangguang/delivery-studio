# 集群与交付重构方案（讨论稿，后续开发以此为准）

状态：设计已与使用者逐条讨论确认。第 12 节的第 1、2、3 步已实现（1.0.76–1.0.79-dev，见第 14 节）；第 11 节列出开发时还需要定的细节。

## 0. 产品定位

平台是一个**中间件架构师系统**：记录并生成各种技术方案与文档。像一位资深架构师一样，接到需求先出方案，部署后交付、写报告、做交接，之后每次变更出新方案，出了问题写复盘。

- 每个集群是一份**案卷**，装着为它做过的所有事和对应的文档。
- 做功能时多问一句：这件事最后能不能落成一份文档、归进案卷。
- 以后新增能力（容量评估、选型建议、架构评审等）都放进同一个案卷，不另起体系。
- AI 的定位是多样的，见第 8.0 节。

## 1. 为什么改

现在顶栏有「交付」和「方案」两个入口，但数据上是同一种东西：一份交付（软件包 + 手册 + 现场执行记录）。「方案」只是带 `intent`（升级 / 补丁 / 扩容 / 缩容）和 `derived_from` 的交付。结果是：

1. 同一个集群的历史被劈成两半：首次部署在「交付」，之后的变更在「方案」。
2. 两个词边界不清，用户不知道自己要做的事该去哪。
3. 新建方案要先去「交付」找基础交付，流程绕。
4. 缺少留存用的「交付报告」。

## 2. 目标模型：以集群为主线

用户的思路是「我有一个集群，要对它做点什么」。所以**集群是主线**，下面挂三样东西：

| 概念 | 是什么 | 说明 |
|---|---|---|
| 方案 | 一份可交给现场执行的材料（软件包 + 步骤 + 手册） | 类型：首次部署、升级、补丁、扩容、缩容、改配置。平台只提供方案，不改集群 |
| 执行记录 | 现场做了什么、做到哪一步、结果与证据 | 沿用现有 runbook / progress 链路 |
| 交付报告 | 集群的「活文档」：架构、规格、版本、每次变更与变更后的样子 | 用于留存，可导出 Word，可按段导出 |

词汇约定：
- 「方案」只指变更，首次部署叫「首次部署」。整套东西统称「交付」。
- `cluster_id` 在系统里全局唯一，是集群的标识，不引入新的集群实体（第一阶段按 `cluster_id` 对已有交付分组）。

## 3. 核心规则

1. **点什么，就只出那一份增量。** 点「扩容」只生成扩容方案，不重复首次部署的内容。
2. **当前状态靠工程师回传确定。**
   - 离线交付：现场在执行记录里确认完成后，方案才计入集群的当前状态。
   - 全自动（将来）：平台自动回传。
3. **同一集群同一时间只有一份未完成的方案。** 有未完成方案时，变更按钮隐藏或置灰（以权限隐藏为准，状态不可用用置灰），并写明原因和跳转链接。
4. **方案的组合由使用者决定。** 平台不强制顺序，但对明确不行的路径拦截：
   - 组件明确声明不可行的路径（如跨大版本升级）：**禁止**。
   - 组件没声明、无法判断的：**警告后允许**。
5. **改配置也是一种方案**，有目标配置与当前的差异、执行步骤、核对步骤。组件需声明哪些配置能在线改、哪些需要重启。
6. **配置被改了，报告里记录**，下一次方案基于记录后的状态。
7. **一个 `cluster_id` 只有一个首次部署。** 新建集群时，`cluster_id` 已存在就拒绝（目前代码没有这个检查，要补）。首次部署失败或作废后，可以在同一集群下重新生成首次部署方案；作废的留在历史里，生效的永远只有一份。

## 4. 方案的状态机

```
已生成 ──开始执行──▶ 执行中 ──全部完成──▶ 已完成
   │                  │  │
   │                  │  └─出错且无法继续─▶ 失败待处理
   │                  │                         │
   └──────作废────────┴─────────────────────────┤
                                                ├─作废（已回到原状）──▶ 已作废
                                                └─完成但有偏差（写明差异）──▶ 已完成（有偏差）
```

- 「已生成 / 执行中 / 失败待处理」都算「未完成」，会锁住集群。
- 「已作废」不改变集群状态，解锁。作废需写原因和操作人。
- 「已完成（有偏差）」：现场实际做了，但和方案不一样。差异进报告，下一次方案基于它。
- AI 提案被接受（对步骤的增加或修改）在执行记录里已有，**自动成为偏差说明的初稿**，工程师确认即可。
- 所有状态变更写操作审计。
- **状态由步骤记录推出，不单独存一份。** 现有的每步结果（完成 / 失败 / 跳过）就是依据：一步都没做 = 已生成；有记录但没做完 = 执行中；全部完成或跳过 = 已完成；有失败 = 失败待处理。只有「作废」和「完成但有偏差」需要工程师明确操作并另存。

## 5. 界面设计

保留现有交付页的整体样式（用户喜欢），只改信息架构。

### 5.1 顶栏
- 去掉「方案」。「交付」仍是第一项。
- 「新建交付」改为「新建集群」，仍沿用现有向导。

### 5.2 交付页（集群列表）
- 一行 = 一个集群：名称（cluster_id）、应用、当前版本、状态；有未完成方案时显示「1 个待执行」小标记，变更过的显示「3 次变更」。
- 搜索、筛选沿用；筛选条件新增「有待执行方案」。

### 5.3 集群详情（右侧详情区，三个页签）
- **概览**
  - 当前架构与规格、版本、节点。
  - 一排动作：升级 / 补丁 / 扩容 / 缩容 / 改配置（受权限和锁规则控制）。
  - 旁边一行输入：「想对这个集群做什么？」（AI，见第 8 节）。
  - 有未完成方案时置顶提示；有「建议的下一步」（来自分阶段升级路线）时显示。
- **方案**
  - 竖向时间线，首次部署在最下面，每次变更往上叠。
  - 每项：类型标签、日期、状态、操作人；可单独下载包和手册；点开进入现有的执行页。
- **报告**（见第 13 节，最终改名「文档」）
  - 预览，右上角「导出 Word」，可勾选范围：全部 / 仅首次部署 / 仅某次变更 / 仅补丁。
  - 文字章节旁有 AI 起草与检查（第 8 节）。

### 5.4 新建变更向导
- 复用现有向导，首页明确写「本次只生成增量方案，不包含首次部署内容」。
- 最后一步的摘要旁有「AI 解读」（用户触发）。

## 6. 交付报告

### 6.1 内容（章节）
1. 封面与基本信息（集群、应用、环境、责任人、日期）
2. 架构与拓扑（程序生成）
3. 规格与版本清单（程序生成）
4. 首次部署记录（程序生成：步骤、结果、偏差）
5. 变更记录（程序生成，按时间；每次变更含类型、原因、前后差异、结果、偏差）
6. 当前状态（首次部署 + 已完成变更的合并结果）
7. 风险与遗留问题（AI 起草，用户确认）
8. 验收结论（AI 起草，用户确认）

**事实一律由平台程序生成，AI 只写解释性文字。**

### 6.2 导出：分开或合并，都支持
- **分开导出**：每一份文档独立成一个 Word（交付报告、某次变更报告、运维交接文档、根因分析报告），也可以按段：仅首次部署、仅某次扩容、仅补丁。
- **合并导出**：勾选多份文档合成一个 Word，按固定顺序排列（封面 → 目录 → 交付报告 → 各次变更 → 运维交接文档 → 附录），统一页眉页脚、页码、目录。
- 界面上是同一个「导出」入口：勾选要导出的内容，下面选「合并成一个文件」或「每份一个文件」（多份时打包为 zip）。
- 导出范围和方式写入审计。

### 6.3 模板
- A：平台内置标准模板，用户可改封面、公司名、章节开关、页眉页脚。
- B：允许用户上传自己的 docx 模板，平台往里填内容（后续做）。
- 数据结构一开始就按「章节 + 数据块」建，所有文档、分开与合并导出、A 和 B 都共用。
- 没确认的 AI 草稿段落：导出前提醒「还有 N 段 AI 草稿没确认」，**不强制**。

## 7. 组件需要补充的声明

| 声明 | 用途 |
|---|---|
| 升级路径 `from → to`（已在 `changes.upgrade` 设计中） | 判断禁止 / 警告 |
| 可在线修改的配置项 | 改配置方案 |
| 每一步的回滚方式（可回滚 / 不可回滚） | 手册里的出错处理；将来自动回滚 |
| 现状核对 | 方案第一步，与记录对不上就停 |

回滚声明值得现在就开始写，对离线手册也有用。

## 8. AI 融入

### 8.0 AI 的角色

AI 不是单一的聊天机器人，同一个 AI 在不同场景扮演不同角色，共用同一套工具、知识库和权限：

| 角色 | 场景 | 做什么 |
|---|---|---|
| 架构师顾问 | 集群问答、讨论方案、选型 | 回答问题、解决问题、讨论架构取舍；遇到含糊先用提问卡片问 |
| 方案与文档助手 | 变更向导、报告、KT、RCA | 起草方案说明与各类文档，检查一致性 |
| 现场排障助手 | 执行页「遇到问题」 | 读执行记录与输出，分析失败，提出步骤修改提案 |
| 组件作者助手 | 组件工作台 | 协助编写组件、运维知识、回滚声明（已有） |
| 将来：评估助手 | 容量评估、选型建议 | 在案卷里产出评估结论，同样落成文档 |

角色由入口决定，不需要用户先选；用户在聊天窗口里也可以直接讨论，不限定在某个步骤里。

### 8.1 原则
1. AI 只给草稿，人确认；改动一律是「待确认」的提案（沿用已定规则）。
2. 事实归平台，文字归 AI。
3. AI 内容可见：带「AI 草稿」标记，确认或修改后才算数，操作写审计。
4. 关掉 AI 也完整可用：未配置时入口消失。
5. 不打断流程：入口是小按钮或一行输入。
6. **信息不够时用提问卡片（`ask_user`，已有）主动问用户，不猜。** 示例见 8.3。

### 8.2 六个位置
1. **集群概览的一句话入口**：「etcd 扩到 5 个节点，新加 10.1.1.8、10.1.1.9」→ AI 判断类型并填好向导表单，用户核对后生成。放在集群概览，不放全局（集群已确定，不用猜）。
2. **向导最后一步的风险解读**：用户触发。跨大版本升级由平台拦截，AI 解释原因并给出分阶段路线，路线落成概览里的「建议的下一步」，一次只执行一步。
3. **现场执行求助**：沿用「遇到问题」「保存并让 AI 分析」。AI 提案被接受时，自动生成偏差说明初稿。
4. **报告文字草稿与检查**：AI 起草第 7、8 章及各章的说明文字；「AI 检查」找报告与执行记录的不一致。
5. **集群层面的问答窗口**：聊天窗口从围绕某份交付改为围绕集群；会话按「集群 → 方案 → 步骤」归类。
6. **安全页直达方案**：看某集群的漏洞时「AI 评估影响」，并一键预填补丁方案。

### 8.3 提问卡片的使用
当用户输入含糊、无法可靠判断时，先问再做。例如：
- 「扩一下」：问「扩哪个组件？加几个节点？新机器的地址？」
- 「升级到最新」：问「目标版本是几？要不要先备份？」（给出可选版本）
- 「改一下配置」：问「改哪一项？需要重启吗？」
能从平台、知识库、集群记录查到的，先自己查，不要问。

### 8.4 将来
审批摘要、漂移解释、回滚建议。界线不变：AI 提议，人批准，平台执行，AI 不下手。

## 9. 全自动交付的预留

现有 ansible 运行器与 playbook 与离线交付同源，所以「自动」是**同一份方案换执行者**。

| 现在就预留 | 离线 | 将来 |
|---|---|---|
| 方案上的 `executor` | `manual` | `platform` |
| 步骤结果的 `source` | `engineer` | `platform` |
| 稳定的步骤编号 | 回传对应哪一步 | 平台逐步执行、逐步记状态 |
| 回传证据的格式 | 日志、截图、文本 | 自动采集，格式一致 |
| 凭据不写进方案 | 只写角色 | 凭据来自部署机 / 凭据库 |
| 步骤幂等 | 现场可重复执行 | 失败可重试 |

将来才加的：部署机接入、审批、预演与维护窗口、失败自动暂停、回滚执行、真实状态探测与漂移检测、软件包下发。

阶段：1) 本文范围，只支持人工；2) 平台执行试点（先做只读现状核对）；3) 审批、回滚、漂移检测。

## 13. 文档体系：不只是交付报告

平台的本质是**记录并生成各种技术方案与文档**。围绕一个集群，最终产出的是一套文档，同一个「章节 + 数据块」的结构，同一套 Word 导出：

| 文档 | 什么时候产出 | 主要读者 | 内容来源 |
|---|---|---|---|
| 交付报告 | 部署完成后，每次变更后更新 | 项目方、留存 | 程序生成事实 + AI 写说明 |
| 变更报告 | 每次变更方案完成后 | 项目方、审计 | 同上，只含这一次变更，可单独导出 |
| **运维交接文档（KT）** | 部署完成后 | 日常运维人员 | 组件作者写的基础内容 + AI 结合本集群架构补全 |
| **根因分析报告（RCA）** | 方案失败或出现故障后 | 技术负责人、客户 | 执行记录 + 失败步骤 + 排查对话，AI 起草，人确认 |

### 13.1 运维交接文档（KT）
面向「集群交出去以后，别人怎么日常运维」：
- 架构说明与各节点角色（程序生成）。
- 日常巡检：看什么、怎么看、正常值是多少。
- 常见操作：启停、备份恢复、日志位置、连接方式。
- **基于本集群架构的典型问题与排查手段**：例如 3 节点 etcd 丢了 1 个怎么办、Patroni 主从切换后怎么确认。
- 变更须知：什么操作要走方案，什么不能直接改。
- 联系方式与升级路径。

内容分两层：
1. **组件作者写基础内容**：每个组件在 `component.yaml` 旁提供运维知识（巡检项、常见故障与排查），工作台里编辑，和手册一起发布。这是质量的下限，不依赖 AI。
2. **AI 补全**：读本集群的实际拓扑、规格、版本、已发生的变更与偏差，在基础内容上补出「针对这个集群」的部分，比如这个集群的节点名、端口、路径、已知偏差带来的注意点。AI 只能补充和细化，不能删改组件作者写的内容；输出都带「AI 草稿」标记，确认后才进文档。
3. 集群发生变更后，KT 提示「架构已变化，建议重新生成」，由用户触发，不自动覆盖。

### 13.2 根因分析报告（RCA）
- 触发：方案进入「失败待处理」，或用户在集群页主动发起。
- 材料（程序整理）：时间线、失败步骤、命令与输出、当时的偏差、相关的 AI 排查对话。
- AI 起草：现象、影响范围、根因分析、处理过程、改进建议。信息不足时先用提问卡片问工程师（例如「失败前有没有人手动改过东西」）。
- 工程师确认并补充后导出 Word；报告挂在失败的方案下，也可以在集群的报告页签里看到。
- 根因结论可以一键存进团队知识库（走已有的「提交后审核」流程），之后别人遇到同样问题 AI 能查到。

### 13.3 对界面的影响
集群详情的「报告」页签改叫「文档」，下面列出：交付报告、变更报告、运维交接文档、根因分析报告，每一项有状态（未生成 / 草稿 / 已确认）、预览、导出。

## 14. 实现记录

### 14.1 第一轮（1.0.76–1.0.79-dev）：集群、方案状态、只含增量的方案

使用者看到的问题：基于漏洞生成的补丁方案里还带着首次部署的环境准备、全套功能测试（含故障切换、时间点恢复）和清理（含"放弃全部备份历史"）；解包命令遇到已有部署目录就停，方案实际跑不通；同一份交付可以生成任意多份方案；方案被迫换了集群标识（`pg-final-c1`）。

已做：

- **集群规则**（`store_cluster.go`）：一个集群标识只部署一次（重复返回 409）；首次部署回传完成前不能生成方案；同一时间只有一份未完成的方案（`holder`）；下一份总是基于最近回传完成的一份（`head`），基于旧的会被拒绝；`Seq` 给方案编号，作废的号不复用。有后续方案的交付不能删除。
- **回传**（`PATCH /api/jobs/:id`，`outcome.tsx`）：完成 / 有偏差（必须写说明）/ 失败 / 作废（必须写说明，之后不能恢复）/ 撤销。之后已有新方案时不能再改。有偏差的说明会用执行中采纳的 AI 步骤修改起草。
- **方案只含增量**（`mwpack`）：方案沿用集群标识，项目和上传包按 `集群.序号` 命名（`pg-demo.02`），放在控制节点上已有项目旁边；只给控制节点和新加入的机器出包；环境准备只核对上传、解包本方案、复制集群现有密码（实际步骤，不再是提示），新机器才做免密；只保留只读检查（合并成"变更后检查"），没有清理；软件仓库只带这次升级和新成员要装的包（只换 Ansible 运行环境的补丁不带仓库，也不改各机器的软件源）。
- **安全只看当前状态**：安全总览、漏洞、CVE、扫描、暂缓提醒只统计每个集群的当前交付（`currentJobs`），被后续方案取代的不再报警。
- **界面**：顶栏去掉「方案」；交付列表一行一个集群；集群详情分"概览 / 方案"；方案打开后是原来的交付详情加回传栏（见 界面设计规范.md 4.1a）。旧链接自动跳到集群里。
- 现有测试数据已清空（使用者同意）。

验证：`TestClusterPlans`（store）与 `TestDeriveChangeOfAPostgresqlCluster`（mwpack，方案只带要装的包）；全量测试通过；真实浏览器在线上实例走了一遍：新建集群 → 首次部署回传完成 → 打补丁 → 占用时其他动作被锁 → 作废（必须写原因）→ 再打补丁（序号 #2、只有控制节点的包、没有仓库）→ 回传有偏差 → 概览和时间线、安全页只看当前；暗色与 560px 窄屏。

线上实例的注意事项：`data/components/` 里的 postgresql 和 etcd 是 10-25 在组件工作台发布过的旧副本（"已修改"），没有 `changes:`，所以线上只能生成"只换 Ansible 运行环境"的补丁，升级和扩缩容不可用；内置版本是有的。

### 14.3 第三轮（1.0.82-dev）：测试补强与集群里的 AI

- **测试**：在临时实例（9443，独立数据库，用完已删除）上用本地替身模型走完整流程：每节 AI 起草、确认、编辑、AI 检查、导出 Word 并用 LibreOffice 渲染核对。发现并修复：执行记录同一秒内的步骤顺序错乱（改按事件顺序）、根因报告的节号跳号、代码块后紧贴的说明、Word 目录在 WPS/LibreOffice 里为空（改为预先填好目录条目）。

### 14.4 第四轮（1.0.83–1.0.88-dev）：补齐剩下的功能与整体界面打磨

功能：

### 14.5 第五轮（1.0.89–1.0.90-dev）：补完除全自动以外的全部规划

- **真实模型**：AI 地址改为 192.168.31.112:3425（密钥不变），两个模型测试通过。文档起草、AI 检查、一句话方案（多轮提问）、方案解读、漏洞评估、集群问答、根因分析提问、容量评估全部用真实模型跑过。
- **修掉的严重问题**：变更方案的离线软件仓库解包到集群的固定目录，首次部署留下的标记让后续方案的解包被跳过，新软件包从未启用；客户端已配置过时也不刷新软件包列表。现在每份方案解包到自己的目录（`/opt/middleware-repositories/<集群>.<序号>`），仓库服务指向新目录并重启，旧目录保留供回退；客户端每次都刷新列表。
- **回退声明**：步骤新增 `rollback`；平台步骤和 5 个内置组件的 43 个变更步骤都写好了；手册和执行页每个会改动机器的步骤都有「出了问题怎么退回」；没声明的步骤在向导里提示；AI 解读按执行顺序说明哪里还能退回。
- **文档过期提示**：交付报告和运维交接里写好的节记录写作时的集群状态，之后集群完成了新方案就标「可能过时」，可以「仍然适用」或「按现在的集群重新起草」。
- **根因分析**：可以为执行顺利的方案或与方案无关的集群故障手动发起；AI 起草时缺少现场才知道的信息会先用提问卡片问，回答保存并附在报告里；手动发起的可以删除。
- **评估报告**：文档页签新增「评估」，容量评估、选型建议；平台带入集群现状（选型还带入平台可用组件），AI 先问业务量、机器配置等，再写分析和结论，结论落到该生成的方案。
- **升级路线（建议的下一步）**：组件声明的升级路径不允许一步到位时，向导提供「按这条路线分步进行」，路线记在集群上，概览显示下一步并一键打开对应版本的升级向导，完成一步自动前进。
- **改配置**：HAProxy、Nginx 也支持（复用校验后再替换的配置任务和平滑重载）；etcd、keepalived 的配置任务会拒绝覆盖已有状态，暂不支持。
- **其他**：「新建交付」改为「新建集群」；AI 页侧栏按 集群 → 方案 → 对话 归类；组件页新增「运维知识」；报告的访问入口说明怎样选到可用节点，安全状况包含运行环境的漏洞并注明比对依据；一句话方案能正确处理新机器的空盘初始化。
